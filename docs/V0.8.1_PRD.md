## 第1章 · 产品概述与目标

- **定位**: 让 v0.8 已建成但 gate 全关的 Skills 体系**安全通电** — 通电前装两套保险 (graceful shutdown + provider 熔断), 通电当日做开闸演练。
- **核心目标** (可量化):
  1. **雪崩防御**: 单 provider 持续失败 ≥5min (窗口失败率 >50%) 后被自动跳过, 恢复后 1 个探针成功即回归 — 三态迁移单测覆盖 100%
  2. **通电验证**: 8 个关闭 gate 全开后, pytest 全绿 (0 skip) + uvicorn 启动冒烟 + 前端 smoke (skill-store 20 卡渲染)
  3. **可观测**: `GET /api/llm/health` 暴露 per-provider state/failure_rate/last_error; 状态迁移 100% 落 audit_log
- **成功指标**: pytest ≥3800 / vitest 425 不变 / tsc 0 错 / **零 skip / 零回归** / `generate_meta.py --check` 过 (routers 73 不变) / 演练报告落档 PROGRESS

## 第2章 · 用户画像与场景

- **画像**: 单人使用, 移动端+桌面双端访问本机 :8898; 每日资讯/周报重度依赖 LLM (summary/digest/skill)。
- **用户故事**:
  - 作为安全从业者, 当 sensenova 持续 5xx 时, 我希望系统自动切到下一个 provider, 以便 20 个 skill 和日常摘要不断供。
  - 作为运维者, 我希望 `/api/llm/health` 一眼看到哪个 provider 被 OPEN、失败率多少, 以便决定手动 reset 或换配置。
  - 作为项目负责人, 我希望七 gate 全开的演练给出明确"通过/不通过"清单, 以便放心保持通电。
  - 作为开发者, 我希望重启后端时在跑的 job/请求被优雅收尾, 以便演练反复重启不丢 WAL 数据。
- **频率**: 演练 1 次 (本批); 日常无感; /health 查看按需 (异常时); 阈值校准演练后 1 轮。

## 第5章 · 业务流分析

- **F1 正常流**: 调用 → breaker.allow()=T → provider 执行成功 → record(ok) → 窗口健康 → 下次照常。
- **F2 降级流**: provider 持续失败 → 5min 窗口失败率 >50% → health 判定 → breaker.trip() OPEN (audit_log) → 后续调用直接跳过该 provider → `_try_order` 落到 fallback 序下一家 (runtime fallback_order 兜底, 非 config 四级链)。
- **F3 恢复流**: OPEN 满 30s → HALF_OPEN 放行 1 探针 → 成功 → reset CLOSED (audit_log); 失败 → 续 OPEN 再等 30s。
- **F4 全挂流**: 5 provider 全 OPEN → `_try_order` 返回结构化错误 (含每家 state) → 上层 (skill_runner/summary) 收到明确失败, 不重试风暴。
- **F5 演练流**: graceful shutdown 落地 → `HOTSPOT_FEATURE_GATES` env 全开 → 重启 → pytest 全量 (0 skip) + 启动冒烟 + 前端 smoke (skill-store 20 卡 / dashboard / settings 17 cat) → 演练报告 → **[假设] 演练通过后 gates 保持全开** (通电目标); 不通过则回关 fail-closed 并把失败项记 PROJECT.md 已知问题。
- **异常流**: 探针失败续 OPEN / 锁竞争 (Lock 保护, 短临界区) / 重启窗口清零 (F1 起步) / 演练中 mock 模式无真实 provider 失败 → **熔断行为在演练中不可验证, 由 test_ai_hub_failover 12 case 承担** (防虚假安心)。

## 第6章 · 操作流分析

- **日常**: 用户无感 — 熔断自动发生, audit_log 留痕, 异常时看 /health。
- **周期**: 演练后阈值校准 1 轮 (真实流量复核 → 写回 llm.yaml 注释); 建议每月看一次 /health 快照。
- **自动化**: CI 门 (generate_meta / check_docstrings / harness_analyze / 零 skip) 不变; breaker 迁移事件 → audit_log 查询可追溯。

## 第7章 · 数据模型设计

- **ProviderHealth** (进程内): `dict[provider, {deque[ts,ok] (5min 判定窗), 1min/1h 展示窗, last_error, last_recorded_at}]` — **判定只用 5min 窗口**; 1min/1h 仅 /health 展示 (审查 P2 降级)。
- **CircuitBreaker** (进程内): `dict[provider, {state, opened_at}]`; `threading.Lock` 全局一把 (临界区微秒级)。
- **llm.yaml 扩展字段**: per-provider `failure_rate_threshold` (0.5) / `recovery_timeout_s` (30) / `scenario_weights` (deep: sensenova>anthropic>ollama...)。
- **audit_log 事件** (复用既有表, 零 migration): `event=dsh_llm_breaker` 风格字段 `provider / from_state / to_state / failure_rate / trigger(health|manual|probe)`。
- **数据流转**: 调用方 (gateway/image) → record → health → trip → breaker → audit_log → /api/llm/health 读侧。**本批零 migration** (复用 audit_log)。

### 审查三 · 第一性原理 — 通过

1. **核心价值一句话**: "20 个 skill 通电时不被单 provider 故障拖垮, 且通电过程本身可控。"
2. **模块服务度**: 8 模块全部直接服务 (graceful 服务"可控", 弹性层服务"不拖垮", 权重表服务"降级质量") — 无删项。
3. **只留 3 个功能**: 演练 / breaker+health / graceful shutdown — 即 MVP, 与 Day 0 + Day 1-3 对齐; P1 两项 (端点/权重表) 是观测与质量增强, 保留但可后移。
4. ⚠️→✅ **P1-2**: 演练跑 mock 模式不产生真实 provider 失败 → 熔断在演练中**不可验证** — 已在 F5 异常流明示"演练验证通电, failover 单测验证熔断", 防虚假安心。

**审查结论**: P0×0 / P1×2 / P2×2, 全部当轮修复入文 (上表 ⚠️→✅ 项); 无阻塞, PRD 定稿 v1.0。
