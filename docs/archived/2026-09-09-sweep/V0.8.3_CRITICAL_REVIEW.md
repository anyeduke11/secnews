# Hotspot v0.8.3 真实架构批判性审查

> 审查日期：2026-09-05。代码基线：`4c686fc33cb1fe79130785f49486398d277a6724`（v0.8.2）。
> 状态：审查与重构设计完成，问题尚未修复，v0.8.3 尚未实现或发布。
> 本文覆盖旧 `CRITICAL_REVIEW_2026-09-03.md` 中有关当前状态的冲突结论；旧文保留为历史。
> 配套：[技术方案](V0.8.3_REFACTOR_PLAN.md)、[业务流与技能契约](V0.8.3_WORKFLOWS_AND_SKILLS.md)。

## 1. 审查结论

现有 Python/FastAPI、React、SQLite/WAL/FTS5 和 llm-wiki-2.0 足以支撑单人本地优先的 B/S 安全工作站。当前主要约束是业务闭环、运行状态真实性和证据质量，不是语言、框架或服务数量。

需要继续建设的产品是 **Hotspot 安全工作站：稳定获取有价值的资讯，以证据形成判断，将判断执行为行动，再把验证结果沉淀为可复用知识**。dsh 和 pi 是内部组件，工作对象是资讯、判断单、行动单、知识条目；对话只是这些对象的辅助操作。

当前不能判定“dsh 大脑 + pi 执行”已完整整合：

- dsh 有进程监督、HTTP 桥和降级辅助类，但现有 HTTP 假设不是本次上游源码的 SDK 接口；技能主执行链没有调用 dsh 规划。
- pi 已有真实协议探针的历史修正和外部 CLI 路径；尚无受管源码依赖、结构化工具执行适配、实时取消和统一模型出站治理。
- 技能注册与直接执行成立，但入队后的生产消费接线缺失，已有五阶段状态机不能等同于自主规划闭环。
- wiki、分块、实体标签和反馈记忆是有效基础，但尚未形成覆盖资讯、判断、行动的证据版本链，也不能把 KL 生命周期命名当成 SAG 检索架构。

## 4. 发现清单

严重级别按影响评定；本次未确认 P0 灾难性故障。下列 P1 是 v0.8.3 对应能力发布的阻断项，不能在文档中直接标成已解决。

### F01 [P1] 生产技能触发停在入队

- 证据：`backend/api/skill_registry_api.py:126` 的 run 只 submit；`backend/services/trigger_gate/worker.py:30` 默认 handler 是 no-op。
- 全 backend 非测试代码检索 `TriggerWorker(` 无实例化点；`backend/main.py:48` lifespan 和 scheduler 未接消费泵。collector/KL 事件 submit 包装也未找到生产调用。
- 数据交叉验证：53 pending、票据关联 skill_runs 为 0。
- 影响：用户点运行获得 ticket_id，但不代表任务会执行；开 gate 不能补上接线。
- 修复：显式生命周期启动 worker，强制绑定 handler；票据和 run 共用关联标识，端到端从 HTTP submit 等到产物。目标结果失败必须映射到票据失败，不能仅凭 handler 未抛错 mark_done。

### F02 [P1] 单源采集落库失败仍报告成功

- 证据：`backend/services/collection_service.py:520` 起，`upsert_many` 异常仅 warning，随后写成功 crawler_run，并按抓得条目数返回 success；accepted_count 直接等于 fetched_count。
- 影响：磁盘、SQLite 或 schema 错误会被表现为正常抓取，健康机还可能复位失败计数。
- 修复：所有入口共享持久化结果信封，区分 fetched/parsed/eligible/persisted/new；保存失败显式 failed，事件在提交完成后发出。

### F03 [P1] 门禁异常时失去收录门槛

- 证据：`backend/collectors/quality_hook.py:53` 配置失败返回 items，`:118` 初始化失败放行，`:145` 门禁异常保留 item；`backend/services/info_filter_gate.py:61` 规则读取失败回落空规则。
- 影响：最需要门槛时门槛失效；丢弃路径又未保证先有可复查原始资料。
- 修复：抓取可以继续，可信收录必须停止；异常资料进入 quarantine，保留 snapshot、rule_version、reason，恢复后可重评。区分不可停的基础准入与可停的个性化筛选 Skill。

### F04 [P1] Skill 归档绕过 WikiFs，失败仍返回路径

- 证据：`backend/services/skill_runner/dispatch.py:321` 的 `_write_wiki` 接受绝对路径并直接 `open(..., 'w')`，未走 WikiFs 原子写与索引链；OSError 在 `:350` 被吞，`:356` 返回路径字符串。
- 影响：归档未成功仍可标成功，同一天固定路径重跑会覆盖，崩溃可留下部分正文；路径和元数据不满足统一存储契约。
- 修复：统一知识提交服务，根目录约束、唯一版本、原子写、hash 验证、索引重建和提交回执。产物存在且验收通过后才能成功。

### F05 [P1] pi 解析还有可复现的成功误判

- 证据：`backend/services/agent_bridge.py:122` 先返回任何先前文本，`:126` 可回退最后一条 JSON；`:267` 以 result 非 None 判成功。
- 本次探针一：只有 `{"type":"session","id":"probe"}`，仍 `classified_ok=true`。
- 本次探针二：assistant 中间文本 `stopReason=toolUse` 后跟 `stopReason=error`，仍返回中间文本并 `classified_ok=true`。
- 修复：按最终 turn/agent terminal、失败类型、工具回执与产物验收判定；无终态、截断、取消、工具失败必须独立表示。现有“user echo 回落 JSON”测试断言也要改变。

### F06 [P1] dsh HTTP 桥与真实上游接口不对齐

- 证据：`backend/services/dsh/bridge.py:37` 假设 POST `/api/task`；本次上游 Python `HarnessClient` 是 stdio JSON-RPC，官方应用支持 sdk/sdk-minimal profiles。
- `backend/api/dsh_api.py:33` 模块级客户端使用初始 endpoint，而 supervisor 配置变更另行读取 settings；控制面配置与任务面可能不同。
- `DshRuntime` 存在降级逻辑，但实际 `/api/dsh/task` 使用直接 HTTP + LLM fallback，不能把 helper 的三态图当成所有调用链事实。
- 修复：改为固定源码的官方 SDK 适配；连接状态、实际执行模式、配置 revision 和 fallback 事实统一返回。LLM 文本降级不得承接需要工具执行的任务。

### F07 [P1] 五阶段外形没有真实规划与有效验收

- 证据：`backend/services/agent_loop/core.py:385` PLAN 默认返回空计划；`skill_runner/core.py:252` 只注入 EXECUTE/REFLECT。
- `skill_runner/core.py:242` 自评未传执行产物；`:244` 使用 `bool(text) or error is None`，文本 `failed` 也判成功，no-op 空输出也可通过。
- 影响：状态机阶段全部完成不等于任务正确完成；新加 dsh 后若保留这一套“认知循环”，还会出现多重规划和反思。
- 修复：dsh 唯一负责认知规划与复盘，Hotspot 负责确定性状态与业务验收；验收输入必须含真实产物、引用和执行回执。

### F08 [P1] Skill API 调用与契约没有守住成功语义

- 证据：`backend/services/skill_runner/dispatch.py:225` 发同机 HTTP，`:242` 未 `raise_for_status`；`skill_runner/core.py:190` 随后直接标 succeeded。
- `skill_registry_api.py:61` 将 Python type 转成类型名字典，不能表达标准 JSON Schema 的 required、enum、范围和嵌套；请求 input 仍是任意 dict。
- 影响：扩展关闭导致 404、服务返回 500，仍可被算作技能完成；前端不能可靠生成表单和验证结果。
- 修复：已知内部能力转显式 ToolRegistry service adapter；保留旧 API adapter 期间严格检查 HTTP 与业务结果。用标准输入/输出 schema 强制两端验证。

### F09 [P1] 并发边界既可能串行，也可能放大

- 证据：`source_scheduler_service.py:74` 三槽位并行调用，`collection_service.py:465` 又用同一个实例锁包住整个单源 I/O，实际该实例跨源串行。
- 去掉锁又会暴露 collector 可变 `sources`；新建多实例则不同实例锁不共享。`utils/concurrency.py:3` 预算按 event-loop 隔离，`agent_loop/core.py:109` 等同步包装每次 `asyncio.run` 创建新 loop。
- 影响：目前的“全局”只在同 loop 成立；dsh/pi 子进程上线后更不能沿用进程内预算假设。
- 修复：不可变 FetchRequest + 独立 parser 调用，按 source/domain 租约；模型出站集中到一个 ai_hub 运行 loop 管理额度，预算等待纳入 deadline。

### F10 [P1] 生命周期与持久知识的真相边界冲突

- 证据：`backend/services/sag_service.py:3` 文档说 md 真源；`:83` 状态推进实际只写 SQLite。`knowledge_links`、实体标签、反馈、任务本就包含非 Markdown 可重建的运行事实。
- `raw_items` 在 `collection_service.py:231` 是收录后的旁路，未覆盖门禁前全部资料；本地 raw 正文非空数为 0。
- 影响：无法承诺“删 SQLite 可全量重建整个系统”，也无法可靠重放当时引用与判断依据。
- 修复：明确 Markdown 管知识正文及语义版本，SQLite 管任务/配置/审批等事务事实，FTS/派生图可重建；原始证据独立不可变快照。跨资源提交用 journal/outbox 和恢复规则。

### F11 [P1] 当前记忆不是完整 SAG 式证据检索

- 证据：已有 `item_entities`、`knowledge_chunks`、`knowledge_links`；`search_service.py:38` 是统一检索，`agent_memory/recall.py:124` 是历史运行相似匹配。
- 本次检查未找到统一的 chunk→语义事件→实体关联→有界查询时展开→原文引用接口；现有 `sag_service` 是生命周期服务。
- 修复：复用 chunks 与实体基础，补语义事件和 evidence ref，将查询时实体扩展纳入可测检索策略；不照搬 SAG 网站、Agent chat 或独立数据库栈。

### F12 [P1] 看板存在合成运行事实

- 证据：`frontend/src/components/dashboard/Dashboard.tsx:44` MOCK_TIMELINE，`:99` 将 14 个 collector 当 active_sources，pending 固定 0，throttle 从启用技能数量推导。
- 影响：即使 53 张票据堵住，UI 仍可显示零待办；信源状态和模型饱和也被错误表达。
- 修复：所有运行事实取后端能力/统计快照；缺数据显示 unknown/unavailable，不合成健康。生产 mock 进入构建检查。

### F13 [P1] 测试隔离声明不覆盖全部用例

- 证据：`backend/tests/conftest.py:296` 的 temp_db 非 autouse；`backend/tests/test_agent_bridge.py:55` 等测试未请求它，`observability_records.py:89` 使用真实连接。
- 本次观察到 315..321 七条模拟记录，历史库也含同类 runner 名称。
- 修复：测试 session 导入生产模块前强制配置三库、wiki、日志和 sidecar home 到临时根；未显式标 live 的测试禁止出网。启动断言防真实目录；先修隔离再跑全量。

### F14 [P2] 前端服务状态缓存、错误和能力启停契约分散

- 证据：`frontend/package.json` 无共享查询库；`frontend/src/lib/api.ts:70` 已有 fetch 封装，但 Sentinel 页面仍各自请求/降级；gate 路由注册是启动快照。
- 影响：多页数字不同、404 与停用混淆、轮询重复，热更新配置并不等于路由即时出现。
- 修复：OpenAPI 类型生成 + TanStack Query 分域迁移 + 持久事件驱动失效；后端返回 effective_enabled、unavailable_reason、pending_restart、revision。

### F15 [P2] 架构资料时序和能力名称误导

- 证据：旧审查仍写断路器缺失/gate 全 false/pi 未实测；PROJECT 中也有旧计数和旧状态。`agent-task-audit` 实际目标是 available agents，并非执行审计。
- 修复：此次文档建立代码基线、现状/目标分栏；交付时以生产闭环测试更新能力矩阵。保留历史记录，新增 superseded 链接，禁止把“已注册”标“可用”。

## 5. 不应重复建设的已有能力

保留 v0.8.1/2 的 provider health、断路器、场景权重、并发辅助、TTL 配置重载、GZip、备份校验；这些确实存在，不重新列成“缺失”。保留 source registry、健康机、URL 防护、质量 pipeline、去重指纹、SQLite/WAL、WikiFs、触发队列、skill registry 和现有路由懒加载，修复其边界与接线。

不以 `except Exception` 数量判定故障，不以 router/service 总数判定必须微服务化，不以没有 SIGTERM 字面量断言没有优雅退出。
