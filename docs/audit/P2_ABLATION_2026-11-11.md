## 1. 方法与口径

### 1.1 实验设计

| 项 | 口径 |
|---|---|
| 观测手段 | 反事实消融：关闭目标能力 → 跑全量回归 → 观察**失败用例差集** |
| 单点性 | 每个对象独立一轮，**不叠加**（避免混淆变量） |
| 基线 | `baseline_all_on` = `conftest` 默认 gate 组合（13 开 / 3 LLM gate 关） |
| 差集定义 | `new = 本轮失败集 − 基线失败集 − 已定性固有失败集` |
| 结论形式 | 「关闭 X → 红：{用例列表}；无变化：{其余}」 |

### 1.2 三类观测维度实况

| 维度 | 实测可用性 | 说明 |
|---|---|---|
| 失败用例差集 | ✅ **有效**（主证据） | 20 轮全部产出可比对差集 |
| 路由数（`app.routes` / `include_router` 计数） | ✅ **有效** | 每轮独立探针，数值随 gate 关闭精确下降 |
| 启动耗时 | ⚠️ **噪声大，仅作参考** | 机器负载相关，见 §4.3 |
| Feed P95 | ❌ **未测** | 本地单用户无稳定 Feed 流量，无法产出可比的 p95 |
| 日志异常数 | ⚠️ **不可比** | 各轮 uvicorn 日志时长随 pytest 时长变化，非固定窗口 |

> **口径诚实声明**：PRD §7.4 设计了 5 个观测维度，实际可得**2 个有效 + 2 个噪声 + 1 个不可测**。本报告结论**只建立在失败差集与路由计数**上。

### 1.3 基线固有失败（已逐项定性，与 gate 无关）

基线 `2 failed, 5425 passed, 7 skipped, 2 errors`（用时 836.6s）。4 项逐项复现核实：

## 4. 观测维度可信度分析

### 4.1 路由数：可信

- 基线 105 routes / 100 included routers，与 `generate_meta.py --check` 报出的 `routers: 100` **一致**（探针口径 = `include_router` 计数）。
- 每个 gate 关闭后路由数**单调下降**且降幅与该 gate 挂载的 router 数**精确对应**（如 `mcp` −5 / `codegarden_phase2b` −2 / `skill_registry` −3）。
- 唯一「例外」：`gate_security_graph` 关闭后路由数**不变** → 但这是**正确设计**而非门禁失效：按 `backend/extensions/__init__.py:114`，该 gate 只控 3 个 job、不占 router。实测 `_is_job_enabled` 三 job 在 gate 关时全部跳过 → **门禁生效**（见 §3.1）。

### 4.2 失败差集：可信

- 20 轮 `total` 恒为 5436（用例集合未变）→ 差集可比。
- `skipped` 恒为 7 → 无跳过率漂移。
- 新增失败全部可归入「被删能力专属测试」或「已识别跨域耦合」，无不可解释项。

### 4.3 启动耗时：噪声大，仅作参考

| 对象 | 冷启动(s) | 备注 |
|---|---|---|
| baseline | 5.16 | |
| `gate_codegarden` | 4.95 | 最快 |
| `gate_skill_registry` | 36.64 | uvicorn 日志显示 15:55:04 启动 → 15:55:08 db initialized（**4s**），但总耗时 36.6s |
| `gate_user_skills` | 91.13 | 日志 16:17:00 → 16:17:34 db initialized（**34s**），迁移阶段耗时异常 |
| `gate_dsh` | 66.11 | |
| `gate_interest_engine` | 10.34 | |

**判定**：耗时差异**与被测 gate 无因果关系** —— `user_skills` / `skill_registry` 关闭本应更快，但实测更慢；日志显示差异集中在 **DB migration 阶段**（磁盘 IO / 机器负载）。**不作为结论依据**。

### 4.4 Feed P95：未测

本地单用户环境无稳定 Feed 流量，无可比 p95 样本。**本轮缺此维度** → 登记为 O-5。

### 5.1.1 实施计划「改测试」清单交叉校验（**发现 1 处过度清单**）

把矩阵实测失败集与实施计划 C3-1 / C3-2 的「改测试」行逐条对撞，发现**计划多列了 3 处摘 router 后不会红的用例**：

| 实施计划列出 | 摘 router 后是否变红 | 实测依据 |
|---|---|---|
| `test_api.py:359-368` `test_trends_default` | ✅ 红 | 矩阵 r01 差集第 1 项 |
| `test_api.py:371-378` `test_trends_by_category` | ✅ 红 | 矩阵 r01 差集第 2 项 |
| `test_api.py:381-383` `test_trends_invalid_hours` | ✅ 红 | 矩阵 r01 差集第 3 项 |
| `test_api.py:187-203` `test_categories_returns_6` | ✅ 红 | 矩阵 r02 差集第 2 项 |
| `test_api.py:206-211` `test_categories_cached` | ✅ 红 | 矩阵 r02 差集第 1 项 |
| `test_feature_gates.py` 的 `/api/trends` `/api/categories` 参数化条目 | ✅ 红 | 矩阵 r01/r02 差集 |
| `test_api.py:567-570` `test_trace_id_middleware_propagates_header` | ❌ **不红** | 该用例只断言 `x-trace-id` 头存在 —— 实测 **404 响应同样带 `x-trace-id`**（中间件在异常路径也打标）→ 端点 404 后断言仍成立 |
| `test_api.py:573-578` `test_trace_id_middleware_uses_provided_header` | ❌ **不红** | 同上（只比对头值） |
| `test_api.py:601/:604` version 不变量端点表 | ❌ **不红** | `test_all_responses_have_version` 有 `if r.status_code == 200` 守卫（`:611`）→ 端点变 404 后**整条被跳过** |

**校正**：实施计划 C3-1/C3-2 的「改测试」清单中，**trace_id 两个用例与 version 不变量用例不属于必改项**（摘 router 后自绿）。但**建议仍改** —— 理由不是「会红」，而是：
- version 不变量端点表（`:601/:604`）继续列 `/api/categories` / `/api/trends` 是**文档性失真**（表里写着不存在的端点），属 R-01/R-02 语义退役的应有清理；
- trace_id 两个用例改用存活端点（如 `/api/hotspots`）可避免「用即将删除的端点做 trace 冒烟」这一脆弱选择。

**处置**：在实施计划 §2 C3-1 / C3-2 的「改测试」行加注「消融实测：其中 3 处自绿，属建议清理非必改」，**不删除原清单条目**（保守：清理成本低、留着的风险是端点表失真）。

### 5.2 对 M-2 路由数目标的影响

M-2 目标 = ≤ 97（口径 `100 − R-01 − R-02 − R-03`）。本矩阵实测：摘除 3 个 router 后 `included_routers` = **99**，而非 97。

**偏差解释**：`r01_trends` / `r02_categories` / `r03_weekly_report` 三轮各自的 `included` 都是 **99**（基线 100，各 −1），即三者**分别**各减 1；三者叠加应为 **97**。因本消融**单点不叠加**，97 的目标值需在 P3 三 commit 落地后**实测确认**，不可由本矩阵直接推出。**不构成 PRD 偏差**，但实施计划 §7 G1 门应以「实测 ≤ 97」为准而非推算。

### 5.3 消融对 R-17（数据架构）的影响

- `gate_dsh` 关闭后 `test_p0_security::test_token_middleware_on_real_app` 红 → DSH 关闭会改变安全中间件的实测路径 → **P2.5 数据架构改造不应与 gate 消融同期进行**（已在实施计划中把 P2.5 排在 P2 之后，顺序正确）。
- 20 轮全量回归均在**同一 `hotspot.db` 副本**上跑（隔离 fixture），未观测到主库体积变化 → 对 R-17 的空间账无影响。
