# Hotspot v0.8.5 方案：v0.8 三层 Sentinel 为底 + v1.0 能力补充

- 日期：2026-09-08；状态：**已裁决实施基线（demo 分支 `feat/v0.8.5-demo`）**。
- 版本口径：v0.8.5 基于 v0.8.2 代码基线的**反向收敛**。v1.0.1（C09-C13）将 v0.8 三层路由物理删除、以 v1 四入口替换的路线被裁决为方向错误；v0.8.5 恢复 v0.8 Sentinel 为唯一壳，v1.0 九领域对象与三类 receipt 降级为嵌入三层的能力区块。
- 本文档是 v0.8.5 的**唯一权威 spec**：路由表（§5）与接口消费表（§6）是一致性门（§10）与流程走查检查单的唯一来源；实现代码与本表冲突时，以同 commit 修正文档或代码，不允许静默漂移。
- 取代的文档：`docs/v1.0/V1.0.1_V0.8_UI_CONVERGENCE_PLAN.md`、`docs/v1.0/V1.0.0_UI_UX_SPEC.md` 中"四入口/V1SentinelShell"条款、`design/UI_UX_CONTRACT.md` 中壳层条款（均已加 superseded 横幅）。

## 0. 裁决理由（第一性原理）

1. 安全从业者的产出 ≈ 单位时间可辩护的结论数 × 每个结论沉淀的可复用率。工作闭环 = 感知→研判→行动→沉淀→更快/更准的下一次。
2. v0.8 三层（资料/判断/行动）是从真实工作流长出来的日活动线，信息密度与动线已被日常使用验证——它是飞轮的**习惯回路**。
3. v1.0 九对象（Material/Signal/Subject/Case/Judgment/Action/Run/Artifact/Knowledge）+ 三类 receipt（evidence/artifact/adoption）给结论以证据链、行动以回执、知识以条件化——它是飞轮的**证据引擎**。
4. **复利的前提是日活，日活的前提是顺手。** v1.0 四入口打破习惯回路 → 没有数据流过 → 复利无从发生。所以 v0.8.5 = 把引擎装回习惯回路。
5. 版本号：`backend/version.py` APP_VERSION 与 `frontend/package.json` → **0.8.5**；demo 合入 main 后打 tag `v0.8.5`。

## 2. 执行结构：实现与验证分离（避免沆瀣一气）

| 角色 | 类型 | 职责 | 权限 |
|---|---|---|---|
| 实现 worker | 主会话/实现 agent | 写本文档、阶段二代码、跑脚本、渲染截图——只提供材料，**不下验收结论** | 写文件 |
| FactCheck agent | Explore（独立、只读） | 本文档逐条对照仓库事实（路由/API/组件/迁移号）→ verdict | 只读 |
| 契约验证 agent | 独立 agent | 执行并判读 G1 + G2 → verdict | 只读+执行脚本 |
| 流程验证 agent | 独立 agent | 从 §6 导出检查单 → 审查 G3 脚本断言严格性 → 执行 → 三态矩阵 → verdict | 只读+执行 |
| 视觉验收 judge | judge agent（独立） | 读 5 断点 PNG，逐页 verdict | 只读 |
| 代码审查 agent | code-reviewer（独立） | 审 demo diff（质量+安全）→ verdict | 只读 |

门禁规则：任何 FAIL → 实现侧修复 → **同一验证角色**重验；验证 agent 只读不写，与实现物理隔离；FactCheck + G1-G4 全 PASS → 交用户终审。用户 = 最终验收人。

## 3. 技术架构

### 3.1 分层（自上而下）

```
SentinelShell（唯一壳：appbar 品牌+三层导航+更多菜单+主题/时钟/设置

  ├─ 判断层 /judge     = SentinelJudgePage（v0.8 判读台）+ CaseQueuePanel（v1 区块）
  ├─ 判断层深链 /cases/:caseId = SentinelShell layer=judge + CaseDetail（v1 提取组件）
  ├─ 行动层 /action    = SentinelActionPage（v0.8 今日行动）+ ExecOverviewPanel（v1 区块）
  └─ 更多菜单 → 工具页（PageLayout+AppNav）：/knowledge(+v1) /skill-store /secnews

                /skills /garden /secrets /sync /dashboard /codegarden /crm /bid-alert ...

```

### 3.2 对象流（能力区块背后的领域链）

Source →（采集/准入 SourcePipeline+admission）→ Material/Signal →（立项）→ Case
→（研判 SK-02）→ Judgment（引用/反证/未知）→（受控执行 SK-03）→ Action → Run → Artifact
→（验收/复盘 SK-04）→ Knowledge（条件化/版本/复查 SK-06）→（复用 SK-05）→ 下一 Case

三类 receipt：evidence_receipts（材料入库幂等）、artifact 校验（hash/verify/accept）、adoption（知识采用回执）。UI 只展示后端 `allowed_actions` 报告的可用动作，页面状态不得替代服务端守卫。

### 3.3 数据流与契约

- REST 为主 + SSE `/api/events`（`last_id` 重放；v1 事件 `v1_signal/v1_judgment/v1_action/v1_artifact/v1_knowledge`）。
- 管道心跳条轮询 `GET /api/sources/health` + `GET /api/kl/pipeline/stats`，后端不可达显示 `…`/unavailable，不伪造零值。
- 类型契约唯一源：`backend/domain/v1_0_models.py` → `scripts/codegen_v1_ts.py` → `frontend/src/domain/v1_0.ts`（CI `--check` 0 drift）。

- **资料层**：v0.8 情报流节奏不变（headline/secondary/flash + 频道 chips + 右栏 rail）；SignalPanel 以「受管信号」区块嵌入（confidence 徽标 verified/likely/unverified、status、material 溯源脚注），每条提供「立项」→ POST cases → `/cases/{id}`。
- **判断层**：v0.8 判读台不变（队列+LLM evaluate+趋势/质量/复利 rail）；CaseQueuePanel 以「Case 队列」区块嵌入（status+priority 徽标、blocked 置顶、点击进 `/cases/{id}`）。
- **`/cases/:caseId`**：CaseDetail（提取自 V1Prototype）——case 头（问题/状态/优先级/关闭按钮）+ Knowledge 区块（reuse receipt）+ Judgment 列表（claim 渲染、引用/证据 refs）+ Action 卡（plan_hash、approve/start/cancel）+ Run 时间线 + Artifact 列表（verify/accept/reject）；走查三路径指示（缺资产/待验收/失败/已拒绝）；`?section=` 锚定滚动。
- **行动层**：v0.8 今日行动三栏不变（reviews/todos/planning-actions）；ExecOverviewPanel 以「执行与验收总览」区块嵌入（8 case 聚合、三态计数、unavailable 降级），点击进 `/cases/{id}?section=actions`。
- 状态语义沿用 v1.0 规范：loading/empty/unavailable/stale/partial/blocked/conflict/failed/accepted 以文字+图标辅助颜色表达；浅/深主题沿用 sentinel.css `--sn-*` token（`index.css` 为真源），**零新增视觉 token，不引入新设计语言**。
