## §1 抽象目标三判据

### 1.1 背景: 能力密集 ≠ 用户可感知

hotspot 是能力密集型系统 (v0.8 实地盘点): 51 scheduler jobs / 404 API endpoints / 107 backend services / 27 collectors。绝大多数能力只以 cron + API 形态存在, 用户感知层 (前端主面板) 只暴露一小部分。"把已有能力抽象成 skill" 的真实诉求**不是再造一层统一接口**, 而是把沉淀的"做事"代码变成用户**看得见、点得动、有反馈**的功能卡片。

### 1.2 三判据

| # | 判据 | 含义 | 不满足的反例 |
|---|------|------|--------------|
| 1 | **复用现成逻辑** | skill 直接调已有 service/repository, 不重复造轮子 | 从零重写一份巡检逻辑 |
| 2 | **LLM 包装增益** | 已有 API/jobs 是结构化输出, skill 加 LLM 摘要 / 归因 / 排序层 | 纯 CRUD 转发, 无任何"翻译" |
| 3 | **用户感知** | 用户能感知 + 触发 + 反馈已有能力 (卡片 / 启停 / 异常标红) | settings_repo 等纯内部服务 |

组合裁决:

- **三条全中 → 强抽象候选** (典型: C 类报告型 — 复用 pipeline 数据 + LLM 摘要 + 用户点卡片看简报)
- **一条有实质增量 且 不触 §3 反模式 → 可抽象** (典型: A 类巡检 — 复用 + 手动触发, 不调 LLM)
- **零增量 → 不抽象** — 抽象等于过度包装, 落入 §3 反模式清单

### 1.3 第一性结论

> 抽象不是为了"统一接口"或"规范命名", 而是为了**让用户从已有能力获得增量价值 (感知 / 触发 / LLM 包装)**。没有增量价值的抽象 = 过度抽象 = 反模式。

三条设计纪律 (结论的直接推论):

1. **只存引用, 不复制逻辑** — SkillDef 用 ServiceTarget/ApiTarget 存 `service.method` 引用; 复制会造成 job / API / skill 三入口行为漂移
2. **默认不调 LLM** — 仅 C 类报告 / D 类分析进入 `ai_hub.summarize()`; 无差别 LLM 包装比直调 API 慢 5-10x
3. **一个 skill = 一个原子用户价值** — 30s-5min 内可完成; 太大 (整个信源系统) 或太小 (单 GET 无格式化) 都是粒度错配

### 1.4 五维风险 — 三判据的批判性审查

三判据回答"为什么抽象", 五维风险回答"抽象会做错什么"。每条风险都有对应的缓解纪律:

| 维度 | 风险 | 反例 | 缓解 (落到本文哪一节) |
|---|---|---|---|
| **重复** | 同一能力 3 处入口 (job / API / skill), 行为漂移 | `collect all hotspots` job + `/api/collect/run` + skill 包装 | 设计纪律 1 只存引用; §3.1/#3.2 |
| **边界模糊** | 哪些抽象哪些不抽象, 缺标准 | 把 `POST /api/knowledge/` 包装成 skill | §2 五类分类法 + §3 反模式清单 |
| **粒度错配** | skill 太大 (整个信源系统) 或太小 (单 GET) | skill 包 30 个 endpoint → 不可调试 | 设计纪律 3 原子用户价值; §2.3/§2.5 陷阱 |
| **上下文丢失** | skill 跑需要 DB session / user_id / feature_gate | skill_runner 不传 user_id → audit 写错用户 | §4.0 契约: RunContext 注入, 不读全局 (A2b 实现) |
| **性能降级** | LLM 包装比直调 API 慢 5-10x | 实时高 QPS 端点包装 → 拖慢主路径 | 设计纪律 2 默认不调 LLM; §3.3 |

### 1.5 判定顺序: 先拦后选

```text
新候选 → ① 反模式清单 (§3; 客观信号由 §5 linter 机器拦)
        → ② 命中任一 → 不抽象 (或 §5.5 人工复议)
        → ③ 未命中 → 人工选 A-E 分类 (§2)
        → ④ 按 §4.0 契约写 SkillDef → A2b 注册 (§6)
```

先拦后选的原因: 反模式是**客观可判定**的 (写方法 / cron 周期 / 热路径关键词), 交给机器; A-E 分类涉及"用户可感知增益"的**主观评估**, 留给人工。机器与人的分界线在 §5.4 固化。

## §2 5 类分类法 (A 巡检 / B 查询 / C 报告 / D 分析 / E 操作)

### 2.1 总表

| 类型 | 判定标准 (用户可感知增益) | 抽象方式 | 是否调 LLM | 示例 |
|---|---|---|---|---|
| **A. 巡检型** | 跑现成 job, 拉结果, 标红异常 | skill → `service.method()` 复用 | 否 | 信源巡检 / secrets 巡检 / migration 一致性 / API 路由健康 |
| **B. 查询型** | 调单 endpoint + 简单格式转换 | skill → httpx GET | 否 | 本周 top 5 / 漏洞数统计 / dsh 任务审计 / feature gate 启用矩阵 |
| **C. 报告型** | 跑 job + LLM 摘要 → 自然语言 | skill → `service.method()` + `ai_hub.summarize()` | **是** | 每日简报 / 周报 / SSO 风险摘要 / 漏洞情报聚合 |
| **D. 分析型** | 多源数据聚合 + LLM 推理 | skill → 多 service 编排 + dsh 评分 | **是** | collector 失败根因 / 跨期事件追踪 / CVE 提及网络 |
| **E. 操作型** | 调现成 API 做写操作, 加审计 | skill → httpx POST + audit_log | 否 | 手动建 ticket / KL rollback / 手动启停 dsh |

分类的三个用途: 决定 SkillDef 形态 (target vs pipeline)、决定 prompt_template 合法性 (仅 C/D)、决定验收口径 (A/B 看结构化输出与标红, C/D 看自然语言质量)。

### 2.2 A 巡检型

特征是把"已经会跑的东西"变成"用户主动要看的东西"。现成 job (如 `source_scheduler_tick` 60s) 的结果只存在日志里, A 类 skill 把它拉出来做成带阈值标红的卡片。实现上是**纯直调**: `target=ServiceTarget(...)`, 零 LLM。陷阱: 巡检结果再过一遍 LLM 总结 — 那是 C 类的增益, A 类加 LLM 属于无差别包装 (违反设计纪律 2); 确要摘要就单独立一个 C 类 skill, 不要污染 A 类的快路径。

### 2.3 B 查询型

特征是"单 GET + 展示层封装"。已有 endpoint 返回结构化 JSON, B 类 skill 只做卡片渲染与预测告警。实现: `target=ApiTarget(path=...)` + `output_formatter`。陷阱: 只调一个 GET 且不做任何格式化 = 包装等于无 (粒度错配) — B 类的合法性**完全来自展示层增益** (卡片 / 阈值 / 趋势箭头), 没有增益就不如让用户直接看现有 UI。

### 2.4 C 报告型

特征是"结构化 → 自然语言"。跑现成 job/service 拿数据, LLM 摘要排序, 落 wiki 归档。实现: `pipeline=[service 拉数, llm 摘要, wiki 落盘]`, **prompt_template 只允许出现在这里与 D 类**。陷阱: 把原始数据全量塞 prompt 爆 token — 应在 service 步骤先做 top-N 裁剪 / 时间窗过滤, LLM 步骤只消费裁剪后的输入。

### 2.5 D 分析型

特征是"跨源关联推理" — 用户手工做不到的那部分。多 service 聚合 + LLM 推理 (根因 / 趋势 / 提及网络), 可叠加 dsh 评分。实现: pipeline 多步编排, 每步一个 service 或一次 LLM。陷阱: 粒度失控 — "collector 失败深度分析"应限定单源/单期 (如"某信源首次出现到稳定趋势"), 全量分析既慢又不可复现。

### 2.6 E 操作型 (v0.9)

特征是"有用户感知的写操作 + 审计"。调现成写 API, 附 audit_log。**v0.8 不落地, 留 v0.9**。注意与反模式 §3.1 的边界: E 类是用户语义上的"动作" (启停 dsh / rollback), 不是内部资源 CRUD; 但二者在 R1 的客观信号上不可区分 (都是 POST `/api/...`), 所以 linter 会一并拦截, 靠 §5.5 人工复议放行 — 这也是 severity=warning 而非 error 的原因。

## §3 7 类反模式清单 (不抽象)

每条按"定义 / 为什么不抽象 / 正确做法"三段式。#1/#2/#3/#4 有 §5 linter 客观信号对应, #5/#6/#7 无客观信号、仅人工判定。

### 3.1 CRUD 内部端点 (linter: R1)

- **定义**: 对 `/api/<resource>` 的资源写操作 (`POST /api/knowledge/`、`PUT /api/knowledge/{id}` 等)
- **为什么不抽象**: wiki-first UI 已提供直接操作入口, 用户可感知增益 = 0; skill 包装反而引入第二入口, 造成行为漂移
- **正确做法**: 不抽象。确属操作动作 (E 类) 时走 §5.5 人工复议

### 3.2 流式 collector (linter: R2, job 视角)

- **定义**: `collect_all_hotspots` 等常驻流式采集, 已有 60s cron
- **为什么不抽象**: 已是后台 job, 用户感知 = "N 分钟后看到新条目"; skill 触发是冗余入口, 且与 cron 竞态
- **正确做法**: 保留 cron。要做"采集健康"相关能力, 抽象成 A 类巡检 (读 collection_logger 统计) 而非触发采集本身

### 3.3 实时高 QPS API (linter: R3)

- **定义**: collect / refresh / run 家族热路径端点
- **为什么不抽象**: skill 包装 (卡片渲染 / 审计 / 潜在 LLM) 在主路径上叠加 5-10x 延迟, 拖慢采集主链路
- **正确做法**: 不包装热路径。健康状态走 A 类巡检旁路观察 (读日志 / 指标, 不进请求路径)

### 3.4 已配 cron 高频 job (linter: R2)

- **定义**: cron_interval_seconds < 300s (5 分钟) 的调度任务
- **为什么不抽象**: skill 触发 = 双调度, 两处入口对同一状态竞争写入
- **正确做法**: 要暴露给用户, 二选一: 降 cron 频率改 skill 手动触发; 或抽象为 A 类巡检 (看结果不触发执行)

### 3.5 LLM 已是核心 (仅人工判定)

- **定义**: chat / free-form prompt 类端点
- **为什么不抽象**: 这就是 chatbox — 与 v0.8 "把 AI 能力固化为可启停功能卡片, 不是聊天框" 的方向相违
- **正确做法**: 把具体场景固化成 C/D 类 skill (明确 input_schema/output_schema), 而不是包装通用对话入口

### 3.6 纯内部服务 (仅人工判定)

- **定义**: settings_repo / user_memory_repo 等无用户感知的内部服务
- **为什么不抽象**: 三判据全不满足 — 无复用增量 (本来就是内部调用)、无 LLM 增量、无用户感知
- **正确做法**: 保持内部。出现感知需求时, 由上游 service 或 A 类巡检聚合后再暴露

### 3.7 MCP 19 tools (仅人工判定)

- **定义**: 已注册的 MCP 工具面
- **为什么不抽象**: 已是 LLM 工具面, skill 包装 = LLM → skill → MCP tool 双跳绕路
- **正确做法**: 不包装工具本体。MCP **可用性**可做 A 类巡检 (前置 gate 检查, mcp=false 时输出 "gate off")

## §4 5 个正反例 + SkillDef 统一契约

### 4.0 SkillDef 统一契约 (A2b 实现基线)

```python
SkillDef(
    id="kebab-case-id",
    runner="builtin",           # 恒为 builtin; LLM 调用只藏在 pipeline 的 Step(kind="llm") 里
    # --- target / pipeline 二选一 (一等公民) ---
    target=ServiceTarget(module=..., class_name=..., method=...),  # 单步: 直调 service
    # pipeline=[Step(kind="service", ...), Step(kind="llm", ...)],  # 多步: 编排
    input_schema={"hours": int},
    output_schema={"health_score": float},
    feature_gate="skill.<id>",  # 每个 skill 独立 gate
    output_formatter=...,       # 可选, B 类卡片渲染
)
```

三条硬规则:

1. **target / pipeline 互斥二选一** — 单步复用走 target, 多步编排走 pipeline; 同时出现即设计错误
2. **只存引用, 不复制逻辑** — target 存 `service.method` 引用由 skill_runner 反射调用; 复制逻辑违反设计纪律 1
3. **prompt_template 仅 C/D 类** — 只允许出现在 pipeline 中 `Step(kind="llm")` 内; A/B/E 类出现 prompt_template 即设计错误 (设计纪律 2)

### 4.1 正例 1 — A 类巡检: 信源质量巡检

- **现成**: `SourceSchedulerService.run_check()` + `source_scheduler_tick` job (60s)
- **skill 增益**: 手动触发 / 异常标红 / 巡检结果落 wiki
- **linter 验证**: `SkillCandidate(kind="service", path="backend.services.source_scheduler_service", name="source-health-scan")` → 零 findings, eligible

```python
SkillDef(
    id="source-health-scan",
    runner="builtin",                    # A 类: 不调 LLM
    target=ServiceTarget(                # 复用 service, 不复制逻辑
        module="backend.services.source_scheduler_service",
        class_name="SourceSchedulerService",
        method="run_check",
    ),
    input_schema={"hours": int, "top_n": int},
    output_schema={"dead_sources": list, "failed_runs": list, "health_score": float},
    feature_gate="skill.source_health_scan",
)
```

### 4.2 正例 2 — C 类报告: 本周 top 5 安全事件

- **现成**: KL pipeline T4 已发布 → `kl_published_items` 表
- **skill 增益**: LLM 排序 + 自然语言摘要 + 落 wiki 归档
- **linter 验证**: service 拉数 (无写方法 / 无 cron / 非热路径) → 零 findings

```python
SkillDef(
    id="weekly-top-events",
    runner="builtin",
    pipeline=[
        Step(kind="service", target=ServiceTarget(..., method="recent_published"), args={"days": 7}),
        Step(kind="llm", prompt_template="从以下事件挑 top 5 并按重要性排序:\n{{ steps.0.output }}"),
        Step(kind="wiki", path="ops/{{ run.date }}-top5.md", content="{{ steps.1.output }}"),
    ],
)
```

**关键**: prompt_template 只出现在 `Step(kind="llm")` — 契约规则 3; LLM 步骤消费的是 service 步骤裁剪后的输出。

### 4.3 正例 3 — B 类查询: Secrets 轮换状态

- **现成**: `GET /api/secrets/rotation-status`
- **skill 增益**: 用户点卡即看当前状态 + 预测告警
- **linter 验证**: GET 读操作 → R1 放行; path/name 无热路径关键词 → R3 放行

```python
SkillDef(
    id="secrets-rotation-status",
    runner="builtin",
    target=ApiTarget(path="/api/secrets/rotation-status"),  # httpx GET
    output_formatter=card_renderer,                          # 展示层封装是 B 类全部增益
)
```

**关键**: 直接调 endpoint, skill 仅做展示层封装; 没有 output_formatter 的 B 类 = 包装等于无。

### 4.4 反例 1 — CRUD 内部: `POST /api/knowledge/`

- **判定**: 用户可感知增益 = 0 (wiki-first UI 已有按钮)
- **linter**: `SkillCandidate(kind="endpoint", path="/api/knowledge/", http_method="POST")` → R1 命中, eligible=False
- **结论**: **不抽象** (反模式 §3.1)

### 4.5 反例 2 — 流式: `collect_all_hotspots` (60s cron)

- **判定**: 已是后台 job, 用户感知 = "5min 后看到新条目"; skill 触发冗余且与 cron 冲突
- **linter**: `SkillCandidate(kind="job", path="collect_all_hotspots", cron_interval_seconds=60)` → R2 命中, eligible=False
- **结论**: **不抽象** (反模式 §3.2 / §3.4)。采集健康诉求改走 A 类巡检

## §5 abstractor 反模式 linter 使用说明

实现: `backend/services/skill_registry/abstractor.py` (纯函数, 无 DB 依赖, 8 个测试用例)。

### 5.1 定位: 机器只拦反模式

linter 是**客观信号拦截器**, 不是 A-E 分类器。"用户可感知增益"是主观判断, 由人工裁决; 机器只负责把三类可机械判定的反模式信号拦下来。这条分界线是刻意的: 让机器做它确定能做对的事, 避免启发式分类给出虚假确定性。

### 5.2 三条规则 (客观信号检查清单)

| 规则 | 信号 (全部客观) | 对应反模式 | severity |
|---|---|---|---|
| R1 CRUD 内部端点 | kind=endpoint 且 http_method ∈ {POST,PUT,PATCH,DELETE} 且 path 匹配 `^/api/[a-z_]+(/.*)?$` (GET 放行) | §3.1 | warning |
| R2 已有高频 cron | kind=job 且 cron_interval_seconds < 300s | §3.2 / §3.4 | warning |
| R3 高 QPS 热路径 | kind=endpoint 且 path/name 含 collect / refresh / run | §3.3 | warning |

### 5.3 使用示例

```python
from backend.services.skill_registry import SkillCandidate, check_candidate

candidate = SkillCandidate(
    kind="endpoint",
    path="/api/knowledge/",
    name="create-knowledge-item",
    http_method="POST",
)
verdict = check_candidate(candidate)
# AbstractorVerdict(
#     eligible=False,
#     findings=[AntiPatternFinding(rule_id="R1", rule_name="CRUD 内部端点", severity="warning", ...)],
# )
```

`find_anti_patterns()` 返回全部命中项 (可为空 / 多条); `check_candidate()` 包装为裁决 — findings 非空 → eligible=False。

对 kind=job 的候选, R2 信号长这样:

```python
candidate = SkillCandidate(
    kind="job",
    path="collect_all_hotspots",
    name="collect-all-hotspots",
    cron_interval_seconds=60,
)
verdict = check_candidate(candidate)
# eligible=False, findings=[AntiPatternFinding(rule_id="R2", rule_name="已有高频 cron", ...)]
```

### 5.4 机器拦什么 / 人工裁什么

| 机器 (linter) | 人工 (review) |
|---|---|
| R1 写方法 + 内部路径形态 | A-E 分类 (§2) |
| R2 cron 周期 < 300s | 用户可感知增益评估 (三判据) |
| R3 热路径关键词 | R1 误报复议 (E 类操作型, 见 §5.5) |
| — | #5/#6/#7 三类无客观信号的反模式 |

### 5.5 已知局限与复议通道

- **R3 子串匹配偏保守** (宁误报不漏报): "run" 可能误中正常命名; 命中后人工看一眼即可放行
- **R1 会拦合法 E 类**: v0.9 的操作型 skill (如包装 `POST /api/dsh/control/start`) 会命中 R1 — 这正是 severity=warning 而非 error 的原因: 拦下来等人工复议, 不是终审
- **复议纪律**: 复议必须留下显式记录 (候选 + 命中规则 + 裁决理由), 禁止静默绕过; waiver 机制在 A2b 落地时一并设计
- **不做 A-E 分类**: abstractor 的 docstring 与本文双重声明 — 分类是人的职责, 机器不越界

## §6 A2a → A2b 工作流

### 6.1 为什么拆两步

原 Phase A2 是"20 skill 静态注册"一锤子活, 风险是一上来拍脑袋列清单。拆成 A2a (原则 + linter) 与 A2b (20 skill 注册) 后, 实现被原则约束: 每个 skill 注册前必须过反模式门 + 显式人工分类, 抽象方向由文档锁定而非实现时即兴决定。

### 6.2 A2b 注册流程 (每个 skill 五步)

1. **草拟候选**: `SkillCandidate(kind/path/name/http_method/cron_interval_seconds)`
2. **过 linter**: `check_candidate()` — findings 非空 → 停: 按反模式处理, 或走 §5.5 复议并记录
3. **人工分类**: 对照 §2 选 A-E, 记录类型与增益理由 (三判据中命中了哪几条)
4. **写 SkillDef**: 按 §4.0 契约 — target/pipeline 二选一, prompt_template 仅 C/D
5. **配 gate + 冒烟**: `feature_gate="skill.<id>"` + 最小运行验证

### 6.3 验收标准 (A2b)

- 20 个 skill 每个有分类记录 (类型 + 增益理由); 对账表见 plan §17.7 (20 skill 全部 A/B/C/D, 无 E, 反模式 0)
- 全部通过 `check_candidate()` (eligible=True 或留有 §5.5 复议记录)
- E 类 (操作型) 留 v0.9; MCP tools 不包装 (§3.7)

### 6.4 常见违规与处理速查

| 违规 | 表现 | 处理 |
|---|---|---|
| 未过 linter 直接注册 | builtin.py 出现 linter 会拦的候选 | 注册流程第 2 步强制, review 拒收 |
| prompt_template 出现在 A/B/E 类 | 巡检 skill 里藏 LLM 摘要 | 拆成独立 C 类 skill (契约规则 3) |
| target 与 pipeline 同时出现 | SkillDef 字段冲突 | 二选一 (契约规则 1) |
| 复制 service 逻辑进 skill | skill_runner 内嵌业务分支 | 改回 ServiceTarget 引用 (契约规则 2) |
| 静默复议 | 绕过 findings 无记录 | 复议必须留候选 + 规则 + 理由 (§5.5) |
