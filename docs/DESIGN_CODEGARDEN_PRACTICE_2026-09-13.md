# CodeGarden 转型设计 — 安全实践域（讨论稿，待裁决）

- 日期：2026-09-13
- 状态：**讨论稿** — owner 裁决 (决策 4)："将 CodeGarden 作为安全实践，属于行动侧，通过研究开源工具和项目进行实践（可以提取前面资讯的开源项目信息）"。本文展开为可实施方向，**未经确认不动代码**
- 定位变化：CodeGarden 从"项目生命周期管理"（当前休眠，全 0 数据）转型为**安全实践域**——行动侧的"练武场"：从资讯流里发现开源安全工具 → 立项研究 → 上手实践 → 产出可沉淀的经验

---

## 1. 转型逻辑（为什么这个定位成立）

现有资产盘点（转型不是从零开始）：

| 既有能力 | 转型后的角色 |
|---|---|
| 资讯流 9,872 条（含大量 AI/安全工具资讯）+ 兴趣引擎 | **实践选题的来源**：从中提取开源项目信号 |
| `POST /api/codegarden/projects/from-knowledge`（已存在！从知识库导入项目） | 选题→立项的现成桥 |
| cg_projects / stages / activities / links（项目+阶段+活动+关联） | 实践项目的容器：研究→部署→验证→复盘 四阶段 |
| cg_dependencies / cg_events（依赖+事件） | 工具链依赖与实验事件记录 |
| playbook_engine / skill（休眠中） | 实践任务的编排执行体（与 P1-0 执行器衔接） |
| Action/Run/Artifact（v1 行动层） | 实践任务作为一类 Action 走"审批→执行→产物"链 |

**闭环**：资讯（看到 Nmap 新脚本）→ 选题入库 → 立项实践 → 上手跑通 → 产出笔记/脚本/复现环境（Artifact）→ 沉淀知识（Knowledge）→ 反哺判断力。

## 2. 四个核心场景（按优先级）

### S1 开源项目信号提取（选题来源）
- **做什么**：从 hotspots/知识库中识别开源安全工具/项目提及（GitHub 链接、工具名、release 新闻），生成"实践候选"清单
- **怎么做**：规则先行（github.com/<org>/<repo> 正则 + 安全域关键词命中）→ 兴趣引擎加权排序 → 候选列表进入"实践选题池"
- **落地位置**：`auto_classifier` 加 practice 信号维度 + 新聚合查询（不动采集链）
- **与决策 6 衔接**：mitre ATT&CK 数据可给项目打"覆盖哪些战术"标签（如 Atomic Red Team → 多战术覆盖）

### S2 实践立项与阶段管理（复用现有 cg_projects）
- **做什么**：候选 → 一键立项（from-knowledge 桥已通）→ 四阶段流：`research`（摸底）→ `setup`（搭环境）→ `exercise`（跑通/演练）→ `retro`（复盘沉淀）
- **改什么**：现有 stages 枚举对齐四阶段；每阶段完成登记 activity
- **与决策 1 衔接**：`exercise` 阶段的执行可走 P1-0 执行器（pi 在边界内跑工具），也可人工

### S3 实践产物沉淀（复用 v1 Artifact + Knowledge）
- **做什么**：每个实践的产出（笔记/命令清单/复现脚本/截图）登记为 Artifact；复盘写 Knowledge（条件化经验："该工具适用于 X 场景，前提是 Y"）
- **价值**：这是"复利律"的兑现——第二次遇到同类工具/场景时，上次实践自动浮现

### S4 工具链健康（保留现有 cg_services/cg_resources 的窄用途）
- **做什么**：本机已部署的安全工具台账（版本/可用性），供 S2 setup 阶段查"我装过什么"
- **克制原则**：不做服务网格/漂移评估（原 phase2b 的 M2-M4 与实践域无关，建议 gate 保持关闭）

## 3. 明确收缩的部分（转型的减法面）

| 原能力 | 处置建议 |
|---|---|
| codegarden_phase2b（服务网格/资源中枢/漂移引擎 M2-M4） | 保持 gate 关闭；若 S4 用不上资源中枢，列入删除候选（下批裁决） |
| github/import、sync、lifecycle 等项目管理功能 | 保留（实践项目管理仍需要） |
| 与 CRM 的残留关联 | 已随 CRM 删除清空 |

## 4. 数据与界面（最小改动面）

- **表**：cg_projects 加 `practice_domain`（对标 interest 8 域）+ `source_hotspot_id`（选题溯源）两列（migration 117）；其余复用
- **界面**：行动侧新增"实践"入口（对齐 NAV4 裁决的行动菜单结构），复用现有 codegarden 组件改造为实践视角；**不动三层壳**
- **API**：候选池查询 1 端点 + 立项 1 端点（from-knowledge 扩展）+ 阶段流转复用现有

## 5. 分期建议

| 期 | 内容 | 验收 |
|---|---|---|
| CP-1 | S1 信号提取 + 候选池（纯读，从存量 9,872 条跑一遍看能提取多少真实项目） | 候选池有 ≥20 条真实安全开源项目 |
| CP-2 | S2 立项四阶段 + 行动侧入口 | 从候选一键立项并走完一个阶段 |
| CP-3 | S3 产物沉淀 + 知识联动 | 一个实践闭环产出 Artifact + Knowledge |
| CP-4 | S4 工具台账 + phase2b 删除裁决 | 台账可用；无用 gate 清理 |

## 6. 需 owner 确认的开放问题

1. **选题口味**：实践候选偏向哪类——渗透工具（offensive）/ 防御检测（detection）/ 两者都要？影响信号提取的关键词表。
2. **实践深度**：候选立项后是"读 README 写笔记"级还是"部署跑通复现"级？影响 setup/exercise 阶段的定义与执行器需求强度。
3. **入口位置**：行动侧新入口 vs 复用现有 /codegarden 页改造？推荐后者改造（避免新一级入口，符合壳纪律）。
4. **与 NAV4 demo 的关系**：四大菜单 demo 中"行动"区已预留实践位——本设计落地时按 NAV4 结构归位。
