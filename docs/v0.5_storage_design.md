## 0. 为什么写这份设计（第一性原理）

实测当前 DB 状态（2026-08-22 08:15）：

```
DB 体积         1.0 GB    (dbstat 685 MB + WAL 54 MB + slack)
DB 行数         4.31 M    (91 个业务表)
最大单表        quality_check_logs_archive  2.65 M 行 / 370 MB  (52% DB 体积!)
次大单表        quality_check_logs          1.21 M 行 / 135 MB  (已声明 weekly cleanup)
第三            raw_items                   138 K 行 /  84 MB
第四            coverage_runs                28 K 行 /  46 MB  (无 retention!)
第五            crawler_runs                162 K 行 /  24 MB
backups/        1.0 GB 残留 (5 份 1GB 全量快照, 老备份从不删)
```

四条硬事实：

1. **DB 真正的膨胀源是质量审计日志，不是业务热点** — quality_check_logs 系
   (live + archive) 占 505 MB / 685 MB = **73.8%** DB 体积。热点 / 收藏 / 知识条目
   加起来不到 50 MB。
2. **WAL 54 MB 没被 checkpoint** — 服务长时间运行但 `wal_autocheckpoint` 没触发或
   触发失败, 导致 WAL 与主库双倍占盘。
3. **旧的全量备份从来没清理过** — 5 份 × 1 GB = 5 GB 备份残留 (单盘工位机致命)。
4. **没有"分类存储"概念** — 所有表共用一张主库文件, 即使热点数据只 2.4 MB 也跟着 1 GB 主库
   一起复制/备份/恢复。**I/O 不分级 = 性价比为零**。

**结论**: v0.5 存储层不是再写一个 ORM, 而是按"数据温度 + 写入频率 + 体量"把数据
**分类到不同的物理文件**, 让热/温/冷/冻各自的备份、清理、加密策略独立。
加增量备份, 让单盘机备份成本从 1 GB → 10 MB/日。

## 1. 数据温度模型（Type-Based Storage）

按"访问频率 × 体量 × 寿命 × 一致性要求"四维, 把 91 张表分到 4 个温度层：

| 温度 | 物理介质 | 默认保留 | 备份频率 | 加密 | 例子 |
|------|----------|----------|----------|------|------|
| **HOT** (热点缓存) | `hotspot.db` 主库 | 30 天 | 增量每日 + 周日 full | 否 | hotspots, favorites, sync_states, settings, security_entities |
| **WARM** (业务流水) | `hotspot-warm.db` ATTACH | 90 天 | 周增量 | 否 | raw_items, crawler_runs, coverage_runs, collection_runs, content_fingerprints, knowledge_tasks, planning_actions |
| **COLD** (审计/历史) | `hotspot-cold.db` ATTACH | 180 天 archive_db_table | 周 full | **Fernet** | quality_check_logs_archive, sync_history_archive, hotspots_archive (180d JSONL → 落 cold) |
| **FROZEN** (资产/真源) | `knowledge/` md + `llm-wiki-2.0/` md | 永久 (git + 增量 zip) | 每周 zip 增量 | 否 (git) | knowledge/*.md, llm-wiki-2.0/*.md, encryption_keys (root key only) |

### 1.1 物理分离的实现

SQLite 支持 **ATTACH DATABASE** 把多个 db 文件逻辑上挂在同一连接下, 但物理独立:

```sql
ATTACH DATABASE 'backend/data/hotspot-warm.db' AS warm;
ATTACH DATABASE 'backend/data/hotspot-cold.db' AS cold;
```

写入用 `INSERT INTO warm.raw_items ...` 或 `INSERT INTO cold.quality_check_logs_archive ...`,
读取走跨库 JOIN 不需要重写 SQL 引擎。

**优势**:
- 备份只拷 HOT → 1 GB → 50 MB
- 清理只 VACUUM WARM → 不影响 HOT 性能
- 加密只针对 COLD → 启动开销只在归档路径
- 单盘机磁盘压力: 主库 50 MB / WARM 200 MB / COLD 1 GB / knowledge md 20 MB

## 5. 分类存储的迁移路径

### 5.1 一次性迁移脚本（v0.5 M2-Task6 新增）

**`scripts/migrate_temp_layers.py`** — 按 retention.json 把表搬到对应 db 文件:

```python
# 设计要点:
# 1. 启动前先做 .bak 副本 (make_backup_snapshot)
# 2. ATTACH warm.db / cold.db
# 3. 跨库 INSERT INTO warm.x SELECT * FROM main.x (按批次, 10k rows/batch, 进度条)
# 4. 主库原表 DELETE FROM (或 DROP, 视迁移信心而定)
# 5. PRAGMA vacuum 单独跑每个 db
# 6. 启动时自动 ATTACH (在 db.get_connection 内置)
```

迁移批次（按依赖顺序, 避免外键冲突）:
1. `crawler_runs` (无 FK) → WARM
2. `collection_runs` (无 FK) → WARM
3. `coverage_runs` (无 FK) → WARM
4. `raw_items` (无 FK) → WARM
5. `quality_check_logs` (无 FK) → WARM
6. `quality_check_logs_archive` (无 FK) → COLD
7. 其余 20+ 张 → WARM (按 dependency DAG 拓扑)
8. `encryption_keys` 留在 HOT (root key, 加密 cold 必需)
9. 启动时 `db.get_connection()` 自动 ATTACH 两个新 db

### 5.2 启动时 ATTACH 机制

```python
# backend/repository/db.py
WARM_DB = BASE_DIR / "hotspot-warm.db"
COLD_DB = BASE_DIR / "hotspot-cold.db"

def get_connection():
    conn = sqlite3.connect(str(HOT_DB), isolation_level="")
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA wal_autocheckpoint=1000")
    conn.execute(f"ATTACH DATABASE '{WARM_DB}' AS warm")
    conn.execute(f"ATTACH DATABASE '{COLD_DB}' AS cold")
    return conn
```

repo 层代码无需改 (如 `crawler_runs` 之前写 `INSERT INTO crawler_runs`, 现在改为 `INSERT INTO warm.crawler_runs`)。
**这要求所有 repo 都升级** → 见 §6 后端映射。

## 7. 安全稳定性（Security & Stability）

### 7.1 加密

| 数据 | 算法 | Key | 备份 |
|---|---|---|---|
| COLD db (`hotspot-cold.db`) | Fernet (AES-128-CBC + HMAC-SHA256) | PBKDF2 派生自 `HOTSPOT_MASTER_KEY` env | 周 full 备份即加密态 |
| 同步 bundle | Fernet envelope | 同 master key | WebDAV 推 |
| `llm_secrets` | Fernet per-row | per-row salt | HOT |
| `encryption_keys` | root key (明文, 单条) | PBKDF2 输入 | HOT (启动期) |
| `api/auth` | 无 (单用户本地) | — | — |

**COLDB 启动加载流程**:
1. 读 `encryption_keys` 表的 root key
2. 解密 `hotspot-cold.db` 的 key header (首 64 字节)
3. ATTACH cold.db, 全程只允许 SELECT, INSERT/UPDATE/DELETE 走 service 层审核

### 7.2 完整性校验

| 备份恢复后 | 命令 |
|---|---|
| 主库 | `PRAGMA integrity_check;` 期望 `ok` |
| 增量链 | 每个 wal-*.bin 头加 sha256, 启动恢复时校验 (M2-T6 待落地) |
| knowledge zip | zip 内含 manifest.json, 解压后 sha256 校验每条 md |
| COLD db | 解密后 `PRAGMA quick_check` |

### 7.3 并发与一致性

- **WORKERS=1** (硬约束, 已在 ARCHITECTURE.md) — 避免 SQLite WAL 多进程锁死
- `wal_autocheckpoint=1000` (WAL → 1000 page 自动 checkpoint)
- ATTACH 后跨库事务 = SQLite 顶层事务 (支持)
- HOT 写后异步 fsync (`PRAGMA synchronous=NORMAL`), WARM/COLD 写用 `FULL` (慢但安全)

### 7.4 故障恢复 RTO/RPO

| 场景 | RTO | RPO | 恢复动作 |
|---|---|---|---|
| 单进程崩溃 | <10s | 0 | supervisor 重启, WAL replay |
| 主库 corruption | <2min | last incremental backup | `restore_from_incremental_chain` |
| 磁盘损坏 | <5min | last full backup | WebDAV 取回 + 增量应用 |
| COLD 损坏 | <1min | 0 (加密态可重跑) | 跑 archive_quality_logs() 重建 |
| knowledge md 误删 | <30s | git HEAD | `git checkout HEAD -- knowledge/` |

### 7.5 备份校验（CI 强制）

`scripts/check_backup_chain.py` (M2-T6 待新增):
- 每周日 backup 完成后, 立即在 tmpdir 跑一次 `restore_from_incremental_chain` + `PRAGMA integrity_check`
- 失败 → 报警到 editorial Today card 红条
- 成功 → 写 `backups/INTEGRITY_OK.{ts}` 标记

## 11. 反向验证（负面测试）

| 测试 | 命令 | 期望 |
|---|---|---|
| 删 master key 后启动 | `unset HOTSPOT_MASTER_KEY; python run.py` | cold db ATTACH 失败, 主库仍工作 |
| 备份 integrity fail | `echo "x" >> backups/hotspot-latest.db; python -c "...restore..."` | `integrity_check` 报 `database disk image is malformed` |
| WAL 损坏 | `truncate -s 100 backend/hotspot.db-wal; python -c "...backup_incremental..."` | 增量失败, 升级 full |
| COLD 加密错 | `HOTSPOT_MASTER_KEY=wrong python -c "...import cold..."` | 解密失败异常, 不 crash 主库 |
| db_diet 误删收藏 | `python -c "...DELETE FROM favorites..."` | favorites 表 trigger 拒 (待 M2-T6 加 trigger) |
| **运行时 VACUUM INTO** | **服务在跑时跑 `db_diet --vacuum-into`** | **M2-T6.4 必须: 检测活跃服务 (PID 或 lock), 拒绝或要求 `--force` + 服务暂停** |

### 11.1 事故记录（2026-08-22 学习）

**事故**：实操 `db_diet --execute --vacuum-into` 时未停服务，导致运行中服务
的旧 fd 仍指向 unlinked inode，与 `shutil.copy2` 新写的主库不一致，
最终 PRAGMA integrity_check 报 `database disk image is malformed`。
**恢复**：从 `/tmp/hotspot.diet.bak` 副本（db_diet 自动建）`cp` 回主库 + `kill` 服务 + `rm -f .db-wal .db-shm`。
**反制（M2-T6.4 必做）**:
- `db_diet --vacuum-into` / `--execute` 前, 必检查 `hotspot.db` 上是否有进程持锁（`lsof` 或 PID file）。
- 若有, 拒绝并提示 "stop service first: `kill $(cat backend/hotspot.pid)` or use `--assume-down` (single-user OK)".
- `--assume-down` 默认开 (单用户工位机), 服务启动时把 PID 写到 `backend/hotspot.pid`。
- 加 `scripts/check_db_integrity.py` 启动 hook: 服务启动时跑 `PRAGMA quick_check`, 失败自动恢复 backup。
