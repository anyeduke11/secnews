## 1. 岗位工作站的信息架构

首版服务单人安全从业者，优先覆盖金融安全、漏洞情报、威胁事件、合规变化与客户/资产影响。岗位关注配置可扩展到其他安全角色，不能把某一人的关键词硬编码进采集器。

主导航：**资讯 / 判断 / 行动 / 知识**。技能中心、信源与规则、dsh/pi 状态置于设置和上下文操作，不增加多个相似首页。

| 入口 | 内容与主操作 | 现有资产如何处理 |
|---|---|---|
| `/` 资讯 | 高价值流、关键变化、待核实、源覆盖；进入详情/生成判断 | 延续 SentinelHome；收藏/搜索/阅读状态保留 |
| `/judge` 判断 | 按问题组织判断单、证据/反证、资产关联、需要复查的结论 | 延续 SentinelJudge；将现有筛选和标记迁入判断对象上下文 |
| `/action` 行动 | 待批准、排队、执行中、待验收、完成/失败；运行详情 | 保留 TODO、复习、现有行动建议；增加 run 关联 |
| `/knowledge` 知识 | 已验证结论、方法、报告、证据检索、相关历史行动 | 复用知识搜索与详情，分层过滤而非另建 wiki |
| `/secnews` | 保留现有六 tab 与深链接，逐项归属上述对象域 | 可作为兼容工作台入口，逐步统一布局与统计 |
| `/skill-store` | 已安装的岗位功能、版本、启停、运行历史；高级配置 | 现有技能商店和 Builder 逐个升级契约 |
| `/dashboard` | 过渡为自动化运行总览，数据来自真实 runs/events | 删除合成时间线与健康值，后续并入同一个工作台 tab |
| `/garden`、`/codegarden`、`/crm` | 项目/环境/客户场景扩展，从行动与判断可进入 | 保留业务入口，不把 `/garden` 偷换成新的知识首页 |
| `/secnews/settings` | 信源、准入、岗位配置、技能、运行时、模型、存储 | 复用 SettingsHub，消除重复的独立管理页面 |

现有链接可以兼容重定向，但迁移前须列出路由、查询参数和受影响测试；不能以“收敛导航”为由静默删除功能。

## 2. 三层业务对象与闭环

### 2.1 资讯层：把值得关注的变化交给人

业务流：源级任务 → 原始证据快照 → 解析/去重 → 基础准入 → 岗位价值排序 → 正式资讯或待核实资料 → 事件聚合。

资讯条目至少展示标题、来源/原文、发布时间与收录时间、价值原因、证据状态、主题/资产关联、新增或更新。正式流默认沿用 `ingested_at DESC`，其他排序显式选择，避免把评分排序误写成“最新”。

同一事件合并多来源，保留首报、官方确认、重要更新和矛盾信息的时间线；转载重复不堆满首屏。抓取失败不伪造旧闻为新资讯，空列表区分“本时段无新内容”和“来源未更新”。

资料池与精选流分开：quarantine 可查看原因、原文、重评入口；rejected 是准入决策而非物理删除。采集低质量样本有保留期限和容量上限，但正式 ingested 历史不得在本次重构中清理。

### 2.2 判断层：把资料变成可审阅的结论

进入方式：资讯勾选“形成判断”、事件聚合自动建议、用户选择岗位模板、已有结论需要复查。

判断单字段：问题、涉及对象、事实、推断、置信、关键证据、反证/缺口、建议行动、适用范围、有效期、版本、责任人。状态为 draft / needs_evidence / ready_for_review / accepted / needs_review / superseded。

dsh 使用证据包形成结构化判断。证据不足返回缺口清单；不能用流畅文本掩盖“没有资产版本所以不能判断是否受影响”。操作包括补资料、修订、确认、暂缓、转行动；每个操作记录对象 revision。

### 2.3 行动层：把结论变成有回执的结果

行动单来自一个或多个判断，必须关联目标、scope、输入证据、所选 Skill/Workflow、预期产物、验收和运行预算。

pi 可执行的首批操作：读取授权资产快照、汇总材料、核对版本清单、生成排查清单和本地报告、调用明确授权的内部工具。外部更改和发布按能力策略执行，不能在读资料任务中自行扩大操作范围。

操作包括运行、取消、批准/拒绝、查看产物、验收、重试可恢复步骤。执行完成但未验收应显示“待验收”，不能直接计入知识成果。失败保留已完成步骤及错误原因，帮助用户决定补参数、重试或人工处理。

### 2.4 回流：一次任务成为下次工作的证据

验收后生成行动复盘：预期/实际差异、有效步骤、无效尝试、环境条件、验证证据、可复用范围、下次复查日期。存为 action 层知识，链接原判断和资讯证据。

下次检索能同时找到原始资讯、当时判断、实际处置结果；模型输出的成功自评不算行动验证。一次失败也可沉淀知识，但标记失败条件，不能当作推荐方案。

## 3. 首批端到端岗位流程

| 流程 | 资讯输入 | dsh 判断 | pi/确定性执行 | 知识回流与验收 |
|---|---|---|---|---|
| 漏洞影响研判 | 官方公告、CVE、厂商版本、补丁变化 | 是否与资产匹配；区分已知/未知/不受影响 | 核对授权资产清单，生成影响矩阵与排查报告 | 结论逐项引用版本依据；人工/测试确认后沉淀处置条件 |
| 每日安全简报 | 高价值事件聚合与更新 | 选择岗位重点和必须跟进项 | 固定 workflow 生成草稿，可由 pi 整理附件 | 每条重点可回原文；阅读反馈只调偏好 |
| 金融合规变化 | 监管原文、新旧条款 | 变化影响、适用业务与待核实项 | 生成条款差异、影响清单、本地任务草稿 | 人工确认法律/制度解释；保存条款版本和修订记录 |
| 客户/项目情报 | 客户相关安全事件、项目资料 | 对客户与机会/项目的影响 | 整理客户简报、建立内部跟进 TODO | CRM 关联与复盘；对外发送独立审批 |
| 信源恢复巡检 | 失败、超时、解析漂移 | 汇总模式，提出恢复建议 | 确定性重试；pi 在隔离样本中验证解析改动 | 不自动改生产源配置；变更验收后记录 parser 版本 |
| 每周知识复盘 | 本周判断、行动、反馈 | 总结有效方法、失效结论和知识缺口 | 更新方法草稿、生成下周待办 | 必须包含真实执行反馈及反证；不能仅重写资讯摘要 |

首个纵向验收案例选“漏洞影响研判”：一次官方公告进入精选 → 判断单 → pi 核对给定资产快照 → 产物验收 → wiki 发布 → 后续相似任务检索引用。测试使用固定公告样本和虚拟资产夹具，live 验收使用授权资料，两者明确分开。

## 5. 标准 Skill 契约示例

以下是拟定的 v0.8.3 manifest，表达语义，不代表现有 loader 已兼容。Tool ID 同样是待登记能力。

```yaml
id: cve-impact-brief
version: 1.0.0
category: judgment
title: 漏洞影响研判
runner: dsh
default_enabled: false
input_schema:
  type: object
  additionalProperties: false
  required: [cve_id, asset_snapshot_id]
  properties:
    cve_id:
      type: string
      pattern: '^CVE-[0-9]{4}-[0-9]{4,}$'
    asset_snapshot_id:
      type: string
      minLength: 1
    evidence_ids:
      type: array
      maxItems: 30
      items:
        type: string
    review_depth:
      type: string
      enum: [standard, extended]
      default: standard
output_schema:
  type: object
  additionalProperties: false
  required: [judgment_id, outcome, evidence_refs, unknowns]
  properties:
    judgment_id:
      type: string
      minLength: 1
    outcome:
      type: string
      enum: [affected, not_affected, unknown]
    evidence_refs:
      type: array
      items:
        type: object
        additionalProperties: false
        required: [evidence_id, revision, chunk_id, content_hash]
        properties:
          evidence_id: {type: string}
          revision: {type: integer, minimum: 1}
          chunk_id: {type: string}
          content_hash: {type: string}
    unknowns:
      type: array
      items: {type: string}
tools:
  - knowledge.search_evidence
  - assets.read_snapshot
  - execution.delegate_pi_readonly
  - judgments.create_draft
side_effect: local_draft
scope:
  asset_source: input.asset_snapshot_id
  network: hotspot_tools_only
trigger:
  manual: true
  automatic: false
budget:
  timeout_seconds: 300
  max_steps: 12
  max_tokens: 24000
  max_cost_usd: 0.50
retry:
  max_attempts: 2
  idempotency: input_revision
artifact_type: judgment
evidence_policy: cited_revision_required
acceptance:
  - output_schema_valid
  - cited_evidence_exists
  - asset_snapshot_revision_matches
  - missing_asset_version_implies_unknown
  - no_external_mutation
ui:
  placement: [information_detail, judgment_toolbar]
  view: judgment_detail
```

schema 有条件约束的地方，acceptance 校验器补充执行，例如 affected/not_affected 必须有支持证据，unknown 必须有未知项。不能只检查字段存在。发布前执行工具 ID 白名单与 scope 校验，前端不提交任意 Tool 名称来扩权。预算数字是示例上限而非模型价格承诺；缺失可核算价格时，不得把未知费用按零处理。

## 6. UI 与交互规格

### 6.1 布局

采用紧凑、可扫描的工作台，沿用 Sentinel 的字号、表格和 CSS token 体系。标题 20..24px，正文 14..16px，元信息 12..13px；固定字号配合换行，禁止视口缩放字体。用层级、列对齐、留白和语义状态突出工作，不用大 Hero、装饰图或大量嵌套卡片。

桌面草图（布局说明，不是生产数据）：

```text
Hotspot   资讯  判断  行动  知识                  搜索 / 通知 / 设置
----------------------------------------------------------------
岗位与时间筛选     待核实 / 待判断 / 待验收 / 来源异常
----------------------------------------------------------------
主题与来源       工作对象列表                     对象详情
资产 / 客户      标题 / 价值原因 / 来源 / 时间      原文与证据
已保存视图       状态 / 更新时间 / 关联事项        判断 / 行动记录
                分页或虚拟列表                    上下文操作
----------------------------------------------------------------
最近刷新时间 / 实时连接状态 / 正在执行的任务入口
```

列宽使用稳定 grid/minmax；右侧详情仅选中对象后出现。1440 桌面可三栏，768 以下筛选收起、列表与详情分层导航，390 手机单列，返回保留筛选与滚动位置。长 URL、CVE、Skill 名字允许断行；按钮不会因为 loading 改变尺寸。

颜色以现有中性色为底，青绿表示正常/完成、琥珀表示待核实/警示、红色表示错误，配文字和图标，不只靠颜色。保留深浅主题，不增加独立紫色/蓝色品牌体系。图谱与来源标识只显示真实数据和可用资产，不作背景装饰。

### 6.2 控件规则

- Skill 启用、自动触发用独立 toggle；运行用图标+短命令；取消/刷新/下载用熟悉图标与 tooltip。
- 类型/状态使用 tabs 或 segmented controls，枚举用选择菜单，数值预算用输入/stepper。
- 空态要说明真实原因并给可执行动作：无新内容、未配置、源不可用、权限不足、待重启不能混为一谈。
- 未接入的能力禁用并显示原因；生产 UI 不展示 mock 正常数值，不显示 API 路径、实现说明或教程式功能介绍。
- 焦点、键盘访问、aria-label、状态变化播报、对比度和 reduced-motion 必须验收；状态转移不把用户焦点抢走。

### 6.3 四种对象详情

| 详情 | 必须展示 | 主命令 |
|---|---|---|
| 资讯 | 原始来源、抓取与发布时间、准入原因、证据/版本、相关事件 | 收藏、形成判断、补资料、查看原文 |
| 判断 | 事实/推断、置信、支持与反证、资产匹配、有效期、修订 | 补证据、确认、修订、转行动 |
| 行动/run | 目标、步骤、实际 runner、预算、等待原因、工具回执、产物/验收 | 运行、取消、批准/拒绝、验收、按步重试 |
| 知识 | 经验证结论、适用条件、来源链、历史行动、失效/修订 | 引用到新判断、修订、安排复查 |

上下文对话放在详情侧栏的“讨论”tab，默认绑定 object_id/evidence_revision。可解释、补参数、纠正判断；保存成 Skill 是显式命令。新对话不会自动变成可信知识或发布权限。页面主体不采用聊天气泡布局。

## 7. 前后端业务状态对照

| 后端事实 | UI 展示 | 允许动作 |
|---|---|---|
| capability installed=false | 未安装 | 查看运行时设置 |
| requested=true / effective=false | 不可用，展示依赖原因 | 修配置/等待重启 |
| queued | 排队中，等待原因 | 取消 |
| running | 当前步骤、真实运行时、已用预算 | 查看、请求取消 |
| waiting_approval | 待批准，具体变更与范围 | 批准/拒绝 |
| cancel_requested | 正在停止 | 查看已发生操作，禁重复取消 |
| committing | 正在归档 | 查看产物，暂不宣称成功 |
| succeeded + acceptance receipt | 已完成/已验收 | 查看知识与复盘 |
| execution complete / human acceptance pending | 待验收 | 接受/退回/补证据 |
| partial | 部分完成 | 查看已完成步骤，重试剩余可幂等部分 |
| failed | 失败与原因 | 修参数或重试 |
| interrupted | 中断，恢复中或待核对 | 仅后端允许时恢复 |
| cancelled | 已取消，保留已发生结果 | 新建运行，不能当作回滚 |
| SSE disconnected | 数据可能陈旧，最后同步时间 | 重连/刷新 snapshot |

其中执行状态与人工验收状态分字段；不为“待验收”伪造另一个执行成功含义。事件流、轮询、列表与详情必须读取相同 aggregate revision，后到的旧响应不能覆盖新状态。

## 8. 端到端验收用例

1. 一条官方漏洞公告：抓取可追溯、基础门禁通过、岗位相关、进入资讯；判断缺资产版本时 outcome=unknown，不能擅自判受影响。
2. 补充资产快照：dsh 生成判断草稿，pi 只读取给定快照，产物逐条有证据；验收后保存 wiki 与索引，下一次查询命中旧判断和实际行动。
3. 来源 HTTP 200 但返回登录/错误页面：不入正式流，quarantine 有原因；UI 保留旧资讯并提示源异常。
4. 门禁配置读取失败：抓取不丢，正式收录不绕过；恢复后同 evidence revision 可重评。
5. 开 Skill 后立即运行、随后停用：requested/effective 和在飞策略一致；pending 不再开始新工作，历史可查。
6. 执行工具之后断进程：恢复器先查回执，不重复产生外部效果；旧 attempt 不能覆盖新 run revision。
7. pi 只有 session/user echo 或中间文本后 error：显示 failed/interrupted，不展示成功。
8. 归档磁盘写失败：run 不成功，产物可重试提交；wiki 无部分覆盖，索引不得指向不存在版本。
9. SSE 断开重连、重复事件、过期游标：页面最终与后端 snapshot 一致，数字不重复增加。
10. mock/fake 测试在隔离目录运行：真实 HOT/WARM/COLD、wiki、sessions 和日志的 hash/计数不变。
11. 旧 `/secnews`、收藏、TODO、CRM、CodeGarden 深链接仍可完成原工作，参数和滚动状态合理保留。
12. 桌面与手机：列表、过滤、详情、批准、取消可达，正文与按钮无重叠，长标题不撑破页面。

以上用例全部与技术方案 release gates 对应；单元测试、设计图、路由存在三者均不能单独替代这些业务验收。

## 9. 第二轮产品审查

- 资讯重要性不等于热度：价值原因须引用岗位与证据，不用点击率主导。
- 自动化不等于无边界：常用能力可以常开，发布和外部更改仍按具体 scope 判断。
- 看板不等于满屏指标：首页重点是待处理对象，运行数字放在状态条与异常入口。
- 知识不等于把全部聊天保存：只有经过验收的可复用产物进入精选知识，原始会话另存作追踪。
- 复利不等于永远强化旧结论：新证据、失败案例、撤回与适用条件变化都能触发复查。
- 多样性与精准性需要一起测：维护官方源和不同类型信源覆盖，避免个性化过滤形成盲区。
- 用户不应理解 dsh/pi 协议才能工作：日常只见任务与结果，运行时详情留在排错面板。
