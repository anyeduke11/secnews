# v0.4.3 重构方案 — 业务架构 / 技术架构 / PRD

> 版本: `v0.4.3` · 基线: `v0.4.0` (commit `741004c`)
> 定位: **结构收敛 + 复利引擎落地** — 不对功能做减法，对复杂度做分层，对闭环做自动化
> 核心理念: 代码是资产，运行时是负债。保留所有资产，收敛所有负债。

---

## 0. 术语表

| 术语 | 定义 |
|------|------|
| **Core** | 直接服务"资料→判断→行动→复利"四根管道的功能，无条件在线 |
| **Extension** | 可插拔功能域，代码完整保留，运行时通过 `feature_gates.toml` 控制可见性 |
| **复利驱动器** | 自动推进闭环的 headless job（不是 UI 功能，是后台引擎） |
| **KL 五阶段** | `kl:raw→kl:refine→kl:link→kl:structure→kl:publish` |
| **SM-2** | SuperMemo 2 间隔复习算法，纯函数实现 |
| **FTS5** | SQLite 全文搜索扩展，CJK 分词支持 |
| **LLM-Wiki** | `knowledge/` 目录即知识库，文件是真相源，DB 是缓存 |

## 一、业务架构

### 1.1 使命（一句话）

> **单人知识工作站：从互联网噪音中提取信号，通过回看与关联沉淀为可复用的个人知识资产。**

### 1.2 价值链（四根管道）

```
Input ──→ 资料 ──→ 判断 ──→ 行动 ──→ 复利 ──→ 复利↗ (回路)
               ↗                                       │
               └──────── feedback loop ────────────────┘
```

每根管道的职责、现有资产、当前状态：

| 管道 | 职责 | 现有资产 | 状态 | 0.4.3 变化 |
|------|------|----------|------|------------|
| **资料** | 全网抓取 → 去重 → 质量打分 → 入库 | 15 collectors + 13 gates + FTS5 | ✅ 完整运转 | 不变 |
| **判断** | raw→publish 五阶段 + 分类 + 关联 + 切块 | KL 状态机 + T1-T5 + auto_classifier(30min/500) + chunk_service | ✅ 管线通，但分类提速不够 | 采集 tail 后即时分类，提升分类覆盖率 |
| **行动** | 知识→待办/草稿/发布/日历排期 | content_service + draft + calendar + publish + todo↔知识转化 | ✅ 管线通，无自动驱动 | 新增：高注意力 items 自动入草稿队列 |
| **复利** | 定期回看 + 关联 + 度量 + 沉淀 | SM-2 + concept_linker + graph_builder + mastery + SOUL + federation | ⚠️ 代码全但缺自动驱动 | 新增：SM-2 每日推送 + 地图每日重建 + 注意力→复习自动转化 |

### 2.2 核心设计原则

| 原则 | 理由 | 实例 |
|------|------|------|
| **物理不搬，软分层** | 300+ 文件 import 图，物理搬迁 = 回归风险 | `core/` 和 `extensions/` 只做 re-export，不搬任何现有代码 |
| **运行时门控，不删代码** | 代码是资产，运行时是负债 | `feature_gates.toml` 控制路由注册 + job 注册 + 前端 tab 渲染 |
| **有消费方 = 存，无消费方 = 熄** | 决定每个 job/router 生死 | 41 job → 35 core + 6 ext，非 35 的停止注册 |
| **复利自动化，不靠人点** | "复利"要求"定期自动推送"，不是 UI 里的"可点" | 4 个 headless 驱动器 |
| **文档追代码，不追人** | 文档漂移是读出成本 | `scripts/generate_meta.py` 从代码反推数字，CI 校验 |
| **冻结基线再动手** | postmortem 经验 1 | 改造前全量测试绿 + 版本 tag |

### 2.4 数据层设计

**表归属（不迁移，只在注释标注）**：

| 表 | 归属 | 备份策略 | 备注 |
|----|------|----------|------|
| `hotspots/items/knowledge_items/chunks/quality_logs/*` | **core** | 每日全量 | 核心数据 |
| `codegarden*` (5 张) | ext-codegarden | 随全局备份 | 不参与 core 数据流 |
| `sync_*` (6 张) | ext-sync | 随全局备份 | 多设备同步 |
| `mcp_tool_registry` | ext-mcp | 随全局备份 | 工具注册表 |

| `security_graph` | ext-security-graph | 随全局备份 | MITRE/CVE |

**数据库不拆分**：单人本地场景，SQLite WAL 单库足够。扩展表数据在磁盘上完整保留，只是 core 代码永不查询它们。

**备份策略（restore 命令）**：
```bash
# 标准 restore (含所有表)
python -m backend.services.backup_service restore --file backups/xxx.zip

# core-only restore (不含扩展表)
python -m backend.services.backup_service restore --file backups/xxx.zip --core-only
```

### 2.6 跨端同步与扩展的关系

**关键决策**：sync 归 extension，但**你的双设备场景需要它**。所以 `feature_sync=true` 默认开启。sync 的数据流只涉及 core 表（`knowledge_items`、`hotspots`、`favorites`...），不会同步扩展表（`cg_*`、`mcp_tool_registry` 被 `sync_bundle.py` 的 `_assert_secrets_sync_safe` 已排除）。即使 sync 默认开，它也不会把 codegarden 数据同步到另一台设备。

### 3.2 四个复利驱动器的详细设计

#### 驱动器①：即时分类（采集 tail 后）

```
现状: auto_classifier 30min/500 条，但采集后新 items 不立即分类
改造: collect_all_job 尾部新增 `_classify_new_items()` 
      → 只对 `ingested_at > last_classify` 的 items 执行分类
      → 不影响原有 30min job (处理历史积压)
验收: 采集完成后，新 items 的 domain/type 不再是 null
```

#### 驱动器②：SM-2 每日推送

```
现状: SM-2 复习靠前端手动点 /api/reviews/due，无主动推送
改造: 新增 cron job `sm2_daily_push` (08:00 Asia/Shanghai)
      → 查询 `review_service.list_due(limit=20)` 
      → 写入 `notifications` 表 (或 knowledge_watcher 写一条通知)
      → 前端 Header 显示 "N 条待复习" 徽标
      → 点击跳转到 /knowledge?mode=review
验收: 每天 08:00 后，前端 Header 出现 "3 条待复习" 徽标
```

#### 驱动器③：地图每日重建

```
现状: map_updater 只在 watchdog 事件触发，新导入大量 items 不重建
改造: 新增 cron job `map_rebuild_daily` (02:00 Asia/Shanghai)
      → 扫描所有 items 的 domain/topic/concepts
      → 重建 _MAP.md (知识地图索引)
      → 重建 graph.json (图谱快照)
验收: 每天 02:00 后，_MAP.md 条目数 ≈ 实际 items 数
```

#### 驱动器④：注意力→复习自动转化

```
现状: attention_events 记录 dwell/scroll/view，但从不自动创建 SM-2 条目
改造: 在 attention_events_api 的写入路径加:
      → 如果 event_type == 'deep_read' 且 dwell_seconds > 30
      → `review_service.create_review(entity_type='item', entity_id=item_id)`
      → 幂等: 同一 item_id 在 24h 内不重复创建
验收: DeepRead dwell>30s 后，/api/reviews/due 中出现该条目
```
