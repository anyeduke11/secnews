### 2.2 核心契约

```python
class CircuitBreaker:                       # backend/utils/circuit_breaker.py
    state: Literal["closed", "open", "half_open"]
    failure_count: int
    opened_at: float
    def allow(self) -> bool                 # open 且未到 recovery_timeout → False
    def record(self, ok: bool) -> None      # 失败 N 次 → open; half_open 成功 → closed
    def reset(self) -> None                 # 手动复位 (对齐 dsh runtime.reset_health 语义)
```

- **调用链**: `services → gateway._try_order → [per-provider: health.allow()? → breaker.allow()? → call → record(ok)] → 全部 OPEN → 4-tier 链最终 fallback (llm.yaml default) → 结构化错误`
- **与 trigger_gate 边界**: trigger_gate 是 **user/入口级**限流 (队列前), breaker 是 **provider/出站级**熔断 (调用前) — 正交不重叠
- **与 dsh runtime 边界**: dsh 的 3 连败缓存保持独立 (进程级子进程语义), 通用 breaker 只管 HTTP 出站; 若抽公共模式需同步迁移 dsh 测试 (裁决点 D2, 默认不抽)
- **可观测**: 每次状态迁移写 audit_log (对齐 Batch 2 LLM provider 审计链); `/api/llm/health` 暴露 state/failure_rate/last_error

## 3. 方案 B: §1.2 断路器 alone — 2 天

只做 `circuit_breaker.py` + ai_hub 单点接入 (D1+D3 精简版), **不做** provider_health 滑动窗口 — 失败计数 = 简单连续 N 次。2 天收口, 但缺健康度/场景/配额感知 (随机抖动会误熔断), §2.1 留 v0.8.2 → 总时长 2+3=5 天且返工接入点。**仅在"本周必须见断路器"的硬约束下选择**。

## 4. 方案 C: §3.1 前端 react-query — 5-7 天

`@tanstack/react-query` (~5KB) + QueryClientProvider + 10 核心组件改造 (Dashboard/SkillStore/SettingsHub 高频端点) + SSE→queryClient 桥。解决 25 处 setInterval 轮询 QPS 倍增 + 离开页面不停轮询。**0 后端改动**风险面在前端, 但 10 组件回归面广、测试 fixtures 全对齐; 不解决 provider 雪崩。适合 A 落地后的 v0.8.2。
