## 0. TL;DR — 一句话方案

**把 hotspot 的 AI 能力重塑为「Skill 商店 + Playbook 引擎」双轨看板**:

- **Skill (内置 + 用户可建)**: 把 ~20 个安全从业者高频场景固化为独立卡片 (信源质量巡检 / 本周 top 5 / SSO 风险摘要 / pipeline 健康自检 / 漏洞情报聚合 / 周报生成 等), 单一 feature gate 独立启停, 一键启动 + 状态可视化 + 历史回放 + 反馈回写
- **Playbook YAML**: 高级用户自编排 (触发条件 → 步骤序列 → 输出落点), 走 codegarden 编排引擎 + agent_loop 状态机
- **触发器 (非聊天)**: 手动按钮 / cron / webhook / KL pipeline 事件 / collector failure, **经 trigger-gate 排队**, 不直接调 LLM
- **dsh 大脑 + pi 执行**: 不变, 但**改名为 Skill Runtime 后端** — Skill/Playbook 的执行就是一次"agent_loop 五阶段"
- **记忆闭环**: 每个 Skill 跑完写 agent_memory, 后续 Skill 自动 recall 相关历史

**4 阶段 × 22 个 commit** (A2 拆 A2a+A2b 后 +1, R-修订), 期末预期:

| 阶段 | 周次 | 核心交付 | 验收 |

## 1. 用户裁决（已锁定, 不再讨论）

### 裁决 1 — 形态: Skill 商店 + Playbook YAML 双轨

| 维度 | Skill (主力) | Playbook (高级) |
|---|---|---|
| **定义** | JSON/YAML 结构化卡片 (prompt + 参数 + 输出模板 + 触发器) | YAML 多步编排 (触发条件 → 步骤序列 → 输出) |
| **作者** | 团队预置 + 用户可视化创建 | 高级用户手写 YAML |
| **粒度** | 单原子任务 (一个 prompt + 一个输出) | 多步骤编排 (可调多个 skill / api / runner) |
| **UI** | Skill Store 卡片 + Skill Builder | Playbook Editor (代码视图) |
| **执行** | 走 skill_runner → agent_loop 五阶段 | 走 orchestrator → 多 agent_loop 实例 |
| **典型用例** | "信源质量巡检" / "本周 top 5" / "pipeline 健康" | "每日 8am 跑信源巡检 → 异常自动建 ticket → 摘要推送到飞书" |

### 裁决 2 — 固化范围: 内置 + 用户可创建

- **内置 ~20 个 skill** (团队预置, 不可删, 可启停): 覆盖安全运营/合规审计/事件分析/日报周报/漏洞情报
- **用户可创建 skill** (Skill Builder UI): 用户填 prompt + 参数 schema + 输出模板 → 存 `user_skills` 表 → 走 feature gate `user_skills=true` 启用
- **不在范围**: 跨用户分享 skill / skill marketplace / 审核流程 (留 v0.9+)

6. **gateway 错误码分布** — 拉 api_events, 按 status_code 聚合 top 20
7. **dsh/pi 任务审计摘要** — 拉 agent_run_records, 按 runner/status/时延聚合
8. **TODO 跨期跟踪** — 扫描 wiki 里 `<TODO>` 标签, 输出超期 7 天清单

### 4.2 合规/审计类 (6 个)

### 4.3 事件分析类 (4 个)
15. **collector 失败事件深度分析** — 单个失败事件 → 拉前后 1h 相关事件 → 推演原因

### 4.4 报告生成类 (2 个)

## 5. Playbook YAML 设计 (Phase C)

### 5.1 字段规范

```yaml
# playbook/examples/daily_source_health.yaml
apiVersion: hotspot/v0.8
kind: Playbook
metadata:
  name: daily-source-health
  desc: "每天 8am 跑信源质量巡检, 异常自动建 ticket"
  owner: builtin
  tags: [operations, daily]

trigger:
  type: cron
  spec: "0 8 * * *"        # 每天 8am
  timezone: Asia/Shanghai

inputs:                       # 用户可覆盖默认
  hours: { type: int, default: 24 }
  top_n: { type: int, default: 10 }

steps:
  - id: scan
    skill: builtin.source-health-scan
    params: { hours: "{{ inputs.hours }}", top_n: "{{ inputs.top_n }}" }
    output: scan_result

  # R8 修订: 删除引用未注册 skill `failure-rate-filter` 的 filter 步, 改为条件内联
  - id: ticket
    if: "{{ steps.scan.output.dead_sources | length > 0 }}"
    type: api
    action: POST /api/codegarden/tasks
    body:
      title: "信源巡检异常 {{ run.date }}"
      body: "{{ steps.scan.output.dead_sources }}"

outputs:
  primary: scan_result
  artifacts:
    - wiki/ops/{{ run.date }}-source-health.md

audit:
  on_failure: retry 1
  on_success: write_audit_log
```

### 7.1 trigger-gate (`backend/services/trigger_gate/`)

**职责**: L1 唯一入口。所有 skill/playbook/手动按钮触发必经此门。

```python
# core.py
class TriggerGate:
    def submit(
        self,
        target_type: Literal["skill", "playbook"],
        target_id: str,
        *,
        inputs: dict = None,
        priority: Priority = Priority.NORMAL,    # REALTIME / NORMAL / BATCH
        source: Literal["manual", "cron", "webhook", "kl_event", "collector_event"],
        user_id: str | None = None,
    ) -> TriggerTicket: ...

# priority.py
class Priority(IntEnum):
    REALTIME = 0    # 手动按钮 / webhook — 出队优先 (R6: 不抢占运行中任务)
    NORMAL = 1      # KL 事件 — FIFO
    BATCH = 2       # cron — 空闲时段

# queue.py — SQLite 持久化, 跨进程可见
class TriggerQueue:
    """ticket 持久化 (trigger_tickets 表, migration 091, R3), ProcessSupervisor 重启不丢"""

# worker.py — 出队泵 (R4 修订: 原方案只画了入队没画消费, 运行时缺"心脏")
class TriggerWorker:
    """进程内单守护线程 — trigger-gate 的消费者:
    - 每 1s 按优先级轮询 SQLite 队列 (REALTIME → NORMAL → BATCH)
    - 出队后派发 runner_pool (3 并发), 自身不执行 skill
    - 崩溃恢复: 启动时扫 status=pending 且超时 ticket, 重新入队
    """

# throttle.py — token-bucket
class TriggerThrottle:
    """per-user 60/min + global 600/min; 超限 429"""
```

**安全边界**:
- webhook 来源校验 (HMAC + **时间戳 ±5min + nonce 防重放** (R7) + IP 白名单), 通过后才入队
- ticket 持久化走 WAL, 进程崩溃不丢
- 优先级仅在**出队时**排序, 不抢占已运行任务 — REALTIME 抢队头不抢执行 (R6: 原"抢占式"与"不互抢"自相矛盾, 定稿为后者)

### 7.3 skill_runner (`backend/services/skill_runner/`)

**职责**: 接收 skill 定义, 调 agent_loop 五阶段, 落产物。

```python
# core.py
class SkillRunner:
    """skill 执行入口 — 一切 skill 调用都走这里"""

    def run(self, skill_id: str, inputs: dict, *, context: RunContext) -> SkillRunResult:
        """五阶段 (C/D 类完整走):
        1. resolve   — 从 registry 取 skill 定义
        2. plan      — 生成调用 LLM 的 prompt + 参数
        3. execute   — 调 ai_hub / runner_pool
        4. reflect   — dsh 评分, 失败 retry 1
        5. commit    — 落产物到 wiki / db / 前端展示

        R2 修订: A/B 类走 fast-path — resolve → execute (直调 target) → commit,
        跳过 plan/reflect (无 LLM 调用可反思), checkpoint 仅记 2 阶段;
        否则 200ms 级查询被五阶段仪式拖慢 10-25x (对抗性审查场景 2)。
        """

# dispatch.py — 按 skill_type 分流派单 (R2)
def dispatch(skill_def: SkillDef, prompt: str, context: RunContext) -> dict:
    # A/B 类: ServiceTarget/ApiTarget 直调, 不经 LLM
    if skill_def.skill_type in ("A", "B"):
        return invoke_target(skill_def.target, context)   # service.method() / httpx
    # C/D 类: 完整五阶段, builtin 走 ai_hub, 其余走 runner_pool
    if skill_def.runner == "builtin":
        return ai_hub_call(prompt, ...)
    elif skill_def.runner in ("pi", "claude-code", "codex"):
        return runner_pool.run(skill_def.runner, prompt, workspace=context.workspace)

# result.py — 产物落点
class SkillRunResult:
    """落点:
    - artifacts: list[WikiPath]     (主产物)
    - metrics: dict                  (耗时/token/成功率)
    - audit_id: str                  (audit_log 引用)
    - run_id: str                    (skill_runs 表主键, migration 091;
                                      RunHistory / Dashboard / 反馈的统一数据源, R3)
    """
```

## 17. 已有能力抽象为 Skill — 第一性原理与批判性审查 (用户追加)

> **用户原话**: "将目前 hotspot 已有能力抽象成 skill, 批判性审查和第一性原理分析和完善"
> **本章目的**: 不是文档综述, 而是回答**"该不该抽象 / 怎么抽象 / 边界在哪"**。

### 17.1 第一性原理 — 抽象的合理性边界

#### 17.1.1 事实盘点 (实地, 非文档)

| 维度 | 数量 | 已 commit |
|---|---|---|
| scheduler jobs | **51** | 路径 `backend/scheduler/scheduler.py` |
| API endpoints (含 GET/POST/PUT/DELETE) | **404** | `grep -E "@router\\.(get\|post)" backend/api/*.py` |
| backend services | **107** | `ls backend/services/ \| wc -l` |
| collectors | **27** | `ls backend/collectors/*.py \| wc -l` |

**密度结论**: hotspot 是**能力密集型系统**, 已沉淀大量"做事"代码。但用户感知层 (前端) 只暴露了一部分。

#### 17.1.2 第一性问题: 为什么要抽象？

剥到最底层, 用户原话拆为三层意图:

1. **复用现成逻辑** — 不重复造轮子, skill 直接调已有 service
2. **加 LLM 包装** — 已有 API/jobs 是结构化输出, skill 加 LLM 摘要/归因/对话层
3. **暴露为可启停功能** — 让用户**感知 + 触发 + 反馈** 已有能力

**第一性结论**:
> 抽象不是为了"统一接口"或"规范命名", 而是为了**让用户从已有能力获得增量价值** (感知/触发/LLM 包装)。**没有增量价值的抽象 = 过度抽象 = 反模式**。

### 17.2 批判性审查 — 5 维度风险表

| 维度 | 风险 | 反模式例子 | 缓解原则 |
|---|---|---|---|
| **1. 重复** | 同一能力 3 处入口: job cron / API endpoint / skill 包装 → 行为漂移 | `collect all hotspots` job + `/api/collect/run` + `source-health-scan` skill | skill **必须复用 service**, 不复制逻辑; skill_registry 存 service.method 引用 |
| **2. 边界模糊** | 哪些抽象哪些不抽象, 缺标准 | 把 `POST /api/knowledge/` (CRUD) 包装成 skill — 用户无感知 | 用 §17.3 五类判定法 + 反例清单 |
| **3. 粒度错配** | skill 太大 (整个信源系统) 或太小 (单 endpoint) | skill 包 30 个 endpoint → 不可调试; skill 只调一个 GET → 包装等于无 | skill = **一个原子用户价值**, 30s-5min 内可完成 |
| **4. 上下文丢失** | skill 跑需要 DB session / user_id / feature_gate 上下文 | skill_runner 不传 user_id → audit 写错用户 | skill_runner 支持 context 注入 (RunContext), 不读全局 |
| **5. 性能降级** | 走 LLM 包装比直调 API 慢 5-10x | 实时高 QPS 端点包装 → 拖慢 | skill 默认**不调 LLM**, 仅在 C 类报告型才调 ai_hub.summarize() |

### 17.3 Skill 分类法 (5 类) + 抽象策略

| 类型 | 判定 (用户可感知增益) | 抽象方式 | 是否调 LLM | 示例 |
|---|---|---|---|---|
| **A. 巡检型** | 跑现成 job, 拉结果, 标红异常 | skill → `service.method()` 复用 | 否 | 信源巡检 / secrets 巡检 / migration 一致性 / API 路由健康 |
| **B. 查询型** | 调单 endpoint + 简单格式转换 | skill → httpx GET | 否 | 本周 top 5 / 漏洞数统计 / dsh 任务审计 / feature gate 启用矩阵 |
| **C. 报告型** | 跑 job + LLM 摘要 → 自然语言 | skill → `service.method()` + `ai_hub.summarize()` | **是** | 每日简报 / 周报 / SSO 风险摘要 / 漏洞情报聚合 |
| **D. 分析型** | 多源数据聚合 + LLM 推理 | skill → 多 service 编排 + dsh 评分 | **是** | collector 失败根因 / 跨期事件追踪 / CVE 提及网络 |
| **E. 操作型** | 调现成 API 做写操作, 加审计 | skill → httpx POST + audit_log | 否 | 手动建 ticket / 手动触发 KL rollback / 手动启停 dsh |

### 17.4 反模式清单 (不抽象)

以下能力**不抽象为 skill**, 抽象等于**过度包装**:

1. **CRUD 内部端点** (`POST /api/knowledge/`, `PUT /api/knowledge/{id}`) — 用户已在 wiki-first UI 直接操作
2. **流式 collector** (`collect_all_hotspots`, 每 60s cron) — 已是后台, 加 skill = 冗余触发
3. **实时高 QPS API** (collect/refresh) — skill 包装拖慢主路径
4. **已配 cron 高频 jobs** (< 5min) — skill 触发等于双调度
5. **LLM 已是核心** (chat / free-form prompt) — 这就是 chatbox, 与方向相违
6. **纯内部服务** (settings_repo / user_memory_repo) — 无用户感知
7. **MCP 19 tools** — 已是 LLM 工具面, skill 包装反而绕路

### 17.5 5 个抽象例子 (正反对比)

#### 正例 1: A 类巡检 — `信源质量巡检`

**现成**: `SourceSchedulerService.run_check()` + `source_scheduler_tick` job (60s)
**skill 增益**: 用户手动触发 / 异常标红 / wiki 报告
**抽象策略**:
```python
SkillDef(
    id="source-health-scan",
    runner="builtin",                    # 不调 LLM
    target=ServiceTarget(                # 复用 service
        module="backend.services.source_scheduler_service",
        class_name="SourceSchedulerService",
        method="run_check",
    ),
    input_schema={"hours": int, "top_n": int},
    output_schema={"dead_sources": list, "failed_runs": list, "health_score": float},
    feature_gate="skill.source_health_scan",
)
```
**关键**: `target` 字段存 service.method 引用, skill_runner **不复制逻辑**, 仅调

#### 正例 2: C 类报告 — `本周 top 5 安全事件`

**现成**: KL pipeline T4 已发布 → `kl_published_items` 表
**skill 增益**: LLM 排序 + 自然语言摘要 → wiki
**抽象策略**:
```python
SkillDef(
    id="weekly-top-events",
    runner="builtin",
    pipeline=[
        Step(kind="service", target=HotspotRepo.recent_published, args={"days": 7}),
        Step(kind="llm", prompt_template="从以下事件挑 top 5 并按重要性排序:\n{{ steps.0.output }}"),
        Step(kind="wiki", path="ops/{{ run.date }}-top5.md", content="{{ steps.1.output }}"),
    ],
)
```
**关键**: 多步 pipeline, 复用 service + 增量 LLM 摘要 + 落 wiki

#### 正例 3: B 类查询 — `Secrets 轮换状态`

**现成**: `GET /api/secrets/rotation-status`
**skill 增益**: 用户点卡 → 看当前 + 预测告警
**抽象策略**:
```python
SkillDef(
    id="secrets-rotation-status",
    runner="builtin",
    target=ApiTarget(path="/api/secrets/rotation-status"),  # httpx GET
    output_formatter=card_renderer,                        # 卡片渲染
)
```
**关键**: 直接调 endpoint, skill 仅做**展示层封装**

#### 正例 4 (反例): CRUD 内部 — `POST /api/knowledge/`

**判定**: 用户可感知增益 = 0 (wiki-first UI 已有按钮)
**结论**: **不抽象**, 包装成 skill = 反模式 §17.4 #1

#### 正例 5 (反例): 流式 — `collect all hotspots` (60s cron)

**判定**: 已是后台 job, 用户感知 = "5min 后看到新条目"
**结论**: **不抽象**, 加 skill 触发反而拖慢 + 与 cron 冲突 (反模式 #2, #4)

### 19.2 第一性原理 — 知识复利三能力拆解

安全从业者的核心价值链 = **资料 (P) + 判断 (J) + 行动 (A)** 三角循环:

```
       ┌──── 资料 (P) ────┐
       │   wiki + FTS5     │
       │   知识沉淀/检索   │
       └──────────────────┘
            ▲           │
            │  P→J      │ J→P
            │  检索     │  产物落库
            │           ▼
┌──────────────────┐    ┌──────────────────┐
│ 行动 (A)         │◄───│ 判断 (J)         │
│ alert + playbook │    │ ai_hub + gateway │
│ 触发 + 编排     │    │ LLM 推理         │
└──────────────────┘    └──────────────────┘
            │           ▲
            │  A→J      │ J→A
            │  复盘     │  决策下发
            └───────────┘
```

| 闭环 | 含义 | hotspot 现状 | 强度 |
|---|---|---|---|
| **P → J** | 资料 → 判断 (RAG) | wiki + ai_hub 走 FTS5 检索 | ✅ 已有 |
| **J → P** | 判断 → 资料 (回写) | ai_hub.write_back 落 wiki | ✅ 已有 |
| **J → A** | 判断 → 行动 (决策) | ai_hub 结论 → alert_engine | ⏳ v0.8 D1 验证 (R10: 实际接线待代码级确认, 未找到明确布线证据) |
| **A → P** | 行动 → 资料 (复盘) | ⚠️ 弱 — alert 处置未自动沉淀 | v0.8 补 Eval + memory |
| **P → A** | 资料 → 行动 (预警) | ⚠️ 弱 — 知识预警未触发 | v0.8 补 Playbook |
| **A → J** | 行动 → 判断 (反馈) | ⚠️ 弱 — 行动结果未反哺 LLM | v0.8 补 HITL |

**6 条闭环中 2 条已强 (P→J / J→P), 1 条待验证 (J→A, R10), 3 条 v0.8 补强 → 期末 6/6 全闭环**。

### 19.3 战略评估 — Skill 化是否能承载知识复利？

#### 19.3.1 Skill 化 ≠ 重建, 是给已有 P/J/A 三层加"用户感知"

| 已有能力 | skill 化增量 | 知识复利贡献 |
|---|---|---|
| `knowledge_items` wiki (P) | skill 产物落 wiki → 资料自然沉淀 | **J → P 闭环自然走通** |
| `ai_hub` 3492 行 (J, R5 修正) | skill 默认调 ai_hub.summarize → LLM 包装自然 | **P → J 闭环自然走通** |
| `alert_engine` 460 行 (A) | skill 跑完 → alert 触达 → 行动自然 | **J → A 闭环走通 (D1 落地时验证布线, R10)** |
| `agent_memory` v2 | skill 反馈 → 偏好挖掘 → 下次更准 | **A → J 闭环自然走通** |
| `playbook_engine` (升级) | 多 skill 编排 → 知识预警触发行动 | **P → A 闭环自然走通** |
| `Eval` + wiki 回写 | skill 跑完自动复盘 → 沉淀经验 | **A → P 闭环自然走通** |

**结论**: skill 化是**给已有 P/J/A 三层加用户感知 + 触发 + 反馈**, 不重写底层。**6 条闭环全部走通** = 知识复利成立。

#### 19.3.2 与"重做 chatbox"路径的对比

| 维度 | skill 化 (现选) | 重做 chatbox |
|---|---|---|
| 工作量 | ~5.5 周 (22 commit) | ~12 周 |
| 复用度 | 100% 复用已有 service | 重写 LLM 调用层 |
| 知识沉淀 | 天然落 wiki | 需自建沉淀机制 |
| 启停控制 | feature_gate 独立 | 需重新设计 |
| 用户感知 | 卡片 + 历史 + 反馈 | 聊天窗口 |
| **契合「专属工作站」** | ✅ 高 | ⚠️ 中 (更像通用助手) |

**结论**: skill 化是**更优战略路径**, 工作量 1/2, 复用度 100%, 契合"专属工作站"定位。

#### 21.2.6 关键交互流 (4 个)

**流 1: 启停 skill**
```
点 [OFF] 徽章 → 二次确认弹窗 → POST /api/skills/{id}/enable
→ 后端写 settings.kv[skill.<id>.enabled] + audit_log
→ SSE event "skill_state_changed" 推送
→ 卡片徽章实时更新 [OFF] → [ON]
```

**流 2: 跑一次 skill**
```
点 [跑一次] 按钮 → 弹参数表单 → POST /api/skills/{id}/run
→ trigger-gate 入队 (priority=REALTIME)
→ 返回 ticket_id → 弹"已入队"提示
→ SSE 订阅 ticket_id → 实时显示阶段进度 (C/D 类 5 阶段; A/B 类 fast-path 2 阶段, R2)
→ 完成 → 跳产物 (wiki 链接 / 卡片摘要) + 反馈按钮
```

**流 3: 编辑 Playbook**
```
点 [新建] → /playbooks?new=true → YAML 编辑器 (monaco)
→ 实时校验 (Jinja + JSON Schema) → 右侧步骤可视化
→ [dry-run] → trigger-gate 入队 (priority=BATCH) → 显示模拟结果
→ [保存] → POST /api/playbooks → 跳详情页
```

**流 4: 查看历史 + 反馈**
```
侧栏 [历史] → RunHistory 列表 (时间倒序, 虚拟滚动)
点单条 → 展开产物面板 (wiki iframe / 摘要卡片 / 错误堆栈)
底部 [👍 评分 1-5] + [评论] → POST /api/skill-runs/{id}/feedback
→ 写 agent_memory.feedback_log → 偏好挖掘异步触发
```

#### 21.3.1 用户旅程 1: 安全运营日常巡检

```
┌─ 08:00 ─────────────────────────────────────────────────────┐
│ cron: daily-source-health playbook 自动触发                  │

│ → 点详情 → 看 wiki 报告 + 跳到 skill 历史                   │

├─ 09:00 ─────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────────┘

#### 21.3.2 用户旅程 2: 手动触发事件分析

```
用户读某条热点 → 点 [深度分析] (D 类 skill)
→ POST /api/skills/event-deep-analysis/run {event_id}
→ trigger-gate REALTIME 优先级入队
→ agent_loop 5 阶段:
   1. intent: "分析 event_id=X 的根因"
   2. plan: 拉前后 1h 事件 + 相似 wiki + CVE 数据库
   3. execute: 并行 3 个 LLM 调用 (事件归因 / CVE 关联 / 风险评级)
   4. reflect: dsh mock 评分, 不达标 retry 1
   5. commit: wiki 落点 + 卡片摘要 + alert 推送
→ 用户看结果 → 👍 → agent_memory 沉淀偏好
```

#### 21.3.3 用户旅程 3: 用户自建 skill

```
Dashboard → [新建 Skill]
→ Skill Builder 4 步向导:
   1. 基本: 名称 / 描述 / 类别 / 图标
   2. Prompt: 编辑器 (monaco + Jinja 语法高亮)
   3. 参数: 动态表单 (拖拽 + JSON Schema 校验)
   4. 输出: 模板 (markdown / 卡片 / wiki)
→ [dry-run] 测试 → [保存] → POST /api/skills (user_skill)
→ settings.kv[user_skills.enabled] = true → 卡片出现在 Skill Store 末尾
→ 反馈循环同内置 skill
```

#### 21.3.4 用户旅程 4: 跨 skill 编排 (Playbook)

```
用户: "每天 8am 跑信源巡检, 异常自动建 ticket"
→ /playbooks?new=true → YAML 编辑器
→ 模板填充 (内置 3 个 example) → 自定义
→ [校验] → 绿色 "✓ 合法"
→ [dry-run] → 模拟跑 → 显示步骤产物
→ [启用] → POST /api/playbooks → cron 注册 (apscheduler)
→ Dashboard 看 playbook 状态 = ON, 下次跑 08:00
→ 第二天 08:00 自动跑 → 用户看触发时间线确认
```

#### 21.3.5 用户旅程 5: 外部系统集成 (Webhook)

```
外部 GitHub: PR 提到 CVE → POST /api/trigger/webhook/github
→ HMAC 校验通过 → trigger-gate 入队 (REALTIME)
→ 自动跑 skill.github-event-handler (C 类)
→ 产物: wiki + slack 通知 + ticket
→ 用户反馈 → 偏好挖掘: "GitHub 触发后必通知 slack" → 自动加到 playbook

#### 21.3.6 用户旅程 6: 跨期趋势追踪

用户: "上周 vs 这周信源质量对比"

→ skill.trend-comparison (D 类, 多源聚合 + LLM)

#### 21.4.2 7 个子系统职责边界

| 子系统 | 职责 | 不做 | 复用 |
|---|---|---|---|
| **trigger_gate** | 入口限流 + 排队 + 三档优先级 + worker 出队泵 (R4) | 不调 LLM / 不跑 skill | — |
| **skill_registry** | skill 注册表 + 启停 + 元数据 | 不跑 skill / 不调 LLM | settings.kv + feature_gates |
| **skill_runner** | 调 agent_loop 跑单 skill | 不编排多 skill | ai_hub + agent_runner |
| **playbook_engine** | YAML 加载/校验/多步骤编排 | 不直接跑 skill | skill_runner + httpx |
| **agent_loop** | 五阶段状态机 + checkpoint | 不持久化 / 不限流 | ai_hub + llm_secrets |
| **agent_memory** | 反馈存储 + recall + 偏好挖掘 | 不调 LLM | user_memory v1 |
| **skill_eval** | 黄金 fixture + 评分 + 报告 | 不跑 skill | ai_hub (judge) |

#### 21.4.4 关键技术决策
