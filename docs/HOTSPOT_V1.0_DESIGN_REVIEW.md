# Hotspot v1.0 功能设计深度审查

> 日期：2026-09-05；对象：[PRD](HOTSPOT_WORKSTATION_PRD_V1.0.md)、[开发方案](HOTSPOT_V1.0_DEVELOPMENT_PLAN.md)、[任务书](HOTSPOT_V1.0_EXECUTION_GUIDE.md)及三份 v0.8.3 附件。
> 方法：先比较需求与约束，再做第一性原理推导、反例审查、六顶思考帽分析，最后把结论回写开发任务与验收。
> 这是设计审查，不是已实现软件的通过报告、用户访谈或独立安全扫描。所有实现项仍待验证。

## 1. 审查结论与主要问题

目标可以用现有技术栈实现。决定成功的不是换框架，而是五条关系是否真实成立：来源与证据、对象与判断、计划与执行、结果与验收、经验与下一次使用。渐进迁移更适合当前已有数据和能力的 Hotspot。

最高优先级风险是旧测试污染真实数据、抓取/发布失败却成功、历史任务被误重放、Agent 自评冒充业务完成，以及切换后丢失新数据。以下按本次方案的风险列出；P1/P2 是审查严重程度，与 PRD 的 P0 功能范围不同。未发现足以断言发生 P0 事故的新证据。

| ID / 级别 | 对照依据与反例 | 设计修订 | 必须拿到的实现证据 |
|---|---|---|---|
| R01 / P1 | 旧审查 F13；直接跑全量可能继续写真实库 | T01 先做 import 前隔离、出网禁止和路径断言 | 原有高风险测试在哨兵/临时根内运行，真实目录不可写 |
| R02 / P1 | 旧审查 F02-F04；抓到内容但保存失败仍绿灯 | T05 先做提交协议，T06 统一计数，T07 准入异常隔离 | 磁盘/DB/配置故障后没有虚假收录/发布回执 |
| R03 / P1 | 旧审查 F01/F07；接 worker 后旧 pending 被重放，旧循环仍自评 | 历史 legacy_hold；dsh 唯一规划；协调器只管状态 | 新旧票据分流；无过期授权重放；实际 handler 失败正确映射 |

| R10 / P1 | 文档内容进入 dsh/pi 后要求越权工具或写 Wiki | 不可信资料仅作证据；受控工具、scope、版本、独立提交 | 注入指令不能改变工具权限/授权范围；结果文件不可执行渲染 |
| R11 / P2 | PRD F05/F11；每条资讯都建事项或六技能各开聊天页 | 明确问题才建 Case、重复追加、上下文继承和一个主动作 | 真实走查无重复粘贴，自动事项/通知预算有效 |
| R12 / P2 | 旧审查 F12/F14/F15；状态乱序、UI mock 和多份旧文档 | 生成契约、revision/allowed_actions、真实 snapshot、版本入口统一 | 两页状态一致、迟到旧响应不覆盖、mock 不进入生产统计 |

## 2. 第一性原理分析

### 2.1 从用户成果推导，而非从组件清单推导

安全从业者投入时间和承担决策成本，最终需要减少不确定性并完成有效工作。将价值拆成可观察的要素：

`净工作价值 = 有效判断和行动带来的收益 + 后续可复用收益 - 阅读/操作/核验成本 - 错误造成的损失`。

这不是用来计算“AI 安全总分”的公式，而是设计取舍框架。增加资讯和报告可能增加成本；减少步骤也可能隐藏必要核验。只有收益与代价一起观察才有意义。

| 基本事实 | 推导出的必要能力 | 反例与验证 |
|---|---|---|
| 没有可追溯输入，就不能检验结论 | 原文版本、出处、hash、时间、引用 | 源网页更改后，旧判断仍能打开旧片段 |
| 影响取决于对象与条件 | Subject revision、未知项、上下文缺口 | 缺资产版本时只能 unknown，不能默认安全 |
| 同一问题持续变化 | Case 关联多版判断与多次行动 | 新公告追加既有事项而非重复造单 |
| AI 文本不是外部效果 | Tool 回执、产物验证、业务验收 | “已处理”文字不能替代实际结果 |
| 执行会失败且网络结果可能未知 | 持久状态、幂等、核对、部分成果 | 工具后失联不会重复变更 |
| 经验只在条件相近时可迁移 | 条件比较、反证、时效、复用回执 | 新版本条件不同会拒绝复用旧结论 |
| 人的注意力有限 | 精选预算、通知合并、明确下一步 | 资料量翻倍不会按比例增加待办 |
| 数据寿命长于一次重构 | 稳定 ID、非破坏迁移、可恢复备份 | 新旧入口能打开同一历史成果 |

### 2.2 必须保持的八个不变量

1. **可信输入**：正式收录必须有已提交证据与准入决策；抓取成功不自动等于收录成功。
2. **版本引用**：判断引用的是具体证据/资产版本；修订不能悄悄更改历史依据。
3. **授权边界**：任务只能调用当前授权的工具与范围；读到的资料不能改变权限。
4. **结果真实性**：技术终态、产物验证和业务验收是三个事实；进程退出和语言自评都不足以证明工作完成。
5. **单一写入者**：同一业务状态只有一个 owner；重试和迁移不得制造两个有效结果。
6. **可恢复提交**：文件与数据库之间的中断可以对账；没有 receipt 的版本不发布。
7. **可撤销知识结论**：新证据可以触发争议与复查；历史不删除，当前可信依据不能继续无提示使用撤回结论。
8. **渐进兼容**：新功能上线不静默丢旧数据/状态/深链接；新写入后的回退必须保全增量。

每个不变量都有 R 风险与 T 任务对应。设计只保留一个组件名而没有实现不变量时，不算实现产品目标。

### 2.3 哪些复杂度可以去掉

- 不先换 FastAPI/React：目前没有证据表明框架阻碍单用户闭环，换框架会消耗迁移预算。
- 不为抓取部署 Agent 循环：协议解析、退避、持久化是可确定的工作，模型波动不应拖停输入。
- 不做第三套认知引擎：Hotspot 管事务与验收；dsh 规划；pi 执行。统一 run_id 不要求统一内部 session。
- 不要求 v1.0 立即合库：单一事务 owner 比物理只有一个文件更关键；现有索引可以保留不同库。
- 不先上图数据库/向量集群：先确认 FTS+实体检索的具体漏召回，再针对效果增加策略。
- 不将每个内部函数 Skill 化：用户 Skill 应表达岗位结果，底层 Tool 和后台设施保持各自职责。
- 不强制每个研究经过实际处置：事项的完成条件按类型决定，避免伪造行动。

不能去掉的复杂度是出处、版本、失败、验收与恢复，它们直接决定产品是否可信。

## 3. 对功能设计逐项施压

| 功能 | 最容易做出的表面实现 | 必须保留的设计 | 验收责任 |
|---|---|---|---|
| 资讯精选 | LLM 打分后列表变短 | 原文完整性、理由、独立召回参考集、未证实通道 | 规则可自动测；岗位价值由用户标注 |
| 事项管理 | 把资讯搬入看板卡片 | 明确问题、完成条件、同问题追加、等待原因 | 用户走查与对象状态测试 |
| 判断 | 一篇流畅总结+引用 URL | 事实/推断、精确片段、未知/反证、条件 | 引用可机械验证；语义支持须独立审阅 |
| 行动 | 一个“执行”按钮和进度动画 | scope、版本、工具回执、部分结果、取消 | 工具与故障测试；实际业务效果独立核验 |
| 经验 | 自动归档每次聊天 | 结果验证、适用条件、失败知识、版本 | 发布规则测试与案例核验 |
| 复用 | 相似度命中旧报告 | 条件比较、采用回执、撤回影响 | 不适用样本、用户采用/效果记录 |
| 能力开关 | 前端 toggle 变色 | 依赖、入队/claim/步骤执行守卫、在飞策略 | 前后端契约和竞态测试 |
| 看板 | 汇总很多数字 | 具体事项、下一步、真实错误、数据时效 | API 对账、浏览器状态与操作测试 |

重要边界：机械校验能证明“引用存在”，不能独自证明“原文支持结论”。模型评审可辅助找问题，但同一个模型生成并自评不是独立效果证据。

## 4. 六顶思考帽分析

六顶帽子是同一方案的六种观察视角，本次没有模拟真实用户访谈或宣称六位独立专家已评审。每顶帽子必须产生设计决定、验证方法或明确保留的问题。

### 4.1 白帽：有什么事实，还缺什么证据

**已知**：四份文档已阅读；当前 APP_VERSION 为 0.8.2；当前 HEAD 比旧审查多一个仅修改 PROJECT.md 的提交。旧审查记录触发消费缺失、抓取/归档成功语义、测试隔离与 UI mock 等问题。本次没有重新抓取数据或验证这些运行缺陷已解决。

**未知**：上游固定 SHA 在用户环境是否可复现构建；当前模型是否支持完整工具回调；关键源连续 7 天表现；首个岗位是否认可筛选；历史数据精确映射成本；实际新手开发速度。

**决定 W1**：先做 T00/T01，再早做 T04；不能把安装成功/历史测试数量作为生产整合证据。

**决定 W2**：统计要保存分母与样本。旧“101 个源、53 pending”等只作历史问题定位，不能成为 v1.0 发布指标或当前事实。

**验证**：baseline、build/protocol/live 三种状态分开；源观察、留出样本和迁移对账分别报告。构建不兼容时更新适配并重锁版本，保留差异记录。

### 4.2 红帽：用户可能怎么感受

以下是待验证体验假设，不是已经收集的反馈：

- 用户可能担心“Agent 在后台到底做了什么”，需要清楚的范围、当前步骤和可停止入口。
- 用户可能讨厌录入资产与建立事项，若每次重复填写，知识复利收益会被操作成本抵消。
- 用户可能对非常自信但无法核对的结论失去信任；承认未知并给出补充动作更有助于继续工作。
- 新手可能把绿色测试和发布成功当作产品有效，需要一条自己能走通的验收故事。

**决定 R-H1**：事项继承证据、资产字段能渐进补充；每天只突出少量下一步，普通运行不刷通知。

**决定 R-H2**：每项输出展示依据、未知和下一步；取消与验收入口在同一事项可见。

**验证**：M0 用现有用户本人走查，再按条件邀请 3..5 位目标用户；观察重复输入、找不到下一步、误以为已处置的次数。无访谈时明确只完成单人可用性验证，不声称覆盖所有安全岗位。

### 4.3 黑帽：哪里最可能失败

| 失败场景 | 后果 | 设计防线与失败时动作 |
|---|---|---|
| 模型/源中断 | 工作台断粮或无故等待 | 输入与认知分池；待深评/故障状态明确，独立重试 |
| 严格精选错杀首报 | 漏重要变化 | 待核实通道和独立召回集；失败先修规则，不下调口径掩盖 |
| dsh/pi 互等配额 | 任务永久运行 | 不持槽位等待委派；deadline、并发 1 测试 |
| 任务重试产生重复效果 | 外部重复写、产物混乱 | 幂等回执、租约 generation；未知效果先核对 |
| LLM 读到“忽略规则” | 越范围操作或知识污染 | 资料和指令隔离，工具端 scope 校验，独立提交/验收 |
| 经验不断自证 | 错误越来越难发现 | provenance、反证、适用条件、撤回和留出集 |
| 新旧系统同时写 | 状态分叉、重复任务 | 单 writer epoch、冻结所有后台 owner、兼容层 |
| 初版范围失控 | 长期无法完成可用版本 | 一案例六能力，分小步；只在闭环成功后扩岗位 |

**决定 B1**：R01-R10 对应能力发布前必须有失败测试和回执证据；不能以“下版再补”关闭。

**决定 B2**：没有真实外部连接器时，业务上明确人工执行并上传结果；不以无权限自动扫描增加表面能力。

### 4.4 黄帽：为什么值得做

**可实现的收益**：采集修好后即使 Agent 未上线，用户也获得更可信输入；证据与上下文继承减少复制；固定能力降低 prompt 编写；有条件的经验复用减少重复取证；保留旧系统资产降低迁移损耗。

**成立条件**：产物确实符合岗位工作，而非增加报告；验收耗时小于节省的工作；少量稳定高价值源足以支持首个任务；固定流程走廉价确定性路径。

**决定 Y1**：每阶段都交可见增量，T06 就能使用改进采集，T12 就能做真实材料工作，不等所有知识模块结束才看到收益。

**决定 Y2**：除完成数外，抽样记录人工取证/核验耗时、模型成本和误判断返工；若净耗时增加，优先修步骤与产物，不添加更多能力。

**验证**：同难度样本与人工基线比较；目标人工主动耗时降低候选 >=30%，同时不能降低证据/判断质量。标签页停留时间不计劳动时间。

### 4.5 绿帽：还有哪些更好的选择

| 可选设计 | 好处 | 代价 | 本次选择 |
|---|---|---|---|
| 全仓重写 | 表面结构整洁 | 丢成熟功能、兼容与恢复负担大 | 不采用；原仓库逐入口替换 |
| 三层页面各自增强 | 改动较小 | 同一问题上下文继续割裂 | 仅保留兼容；新主线使用 Case |
| 所有任务均 dsh+pi | 编排看起来统一 | 双循环耗时、故障面与费用 | 固定 workflow 快路径；不确定任务才协同 |
| 立即单库+新检索引擎 | 架构外观简单/能力多 | 同时迁数据和语义，难以归因 | 事务归属先统一，物理合库与引擎效果驱动 |
| 每条资讯自动建立事项 | 不漏待办 | 大量噪声和录入负担 | 建议为默认，自动建项显式规则和数量预算 |
| 经验直接升级成 Skill | 快速“自进化” | 未验证流程放大错误 | 从验收事项提取候选，回放评测后人工发布版本 |
| 先做全功能 Skill Builder | 适配岗位广 | 首期复杂度与执行边界扩大 | 六个受管包，Builder 后置 |

**决定 G1**：保留“研究型事项”以适配不需要实际执行的问题；“行动型事项”仍要真实结果。

**决定 G2**：报告只是 Artifact 的一种。影响矩阵、排查清单、对比表、复用条件差异应结构化展示，避免用户从长报告重新摘录。

**验证**：用同一问题比较“全文报告”和“结构化结果+证据”所需操作；保留信息完整性和导出能力。

### 4.6 蓝帽：如何让分析变成执行控制

由一份任务台账管理依赖与证据；DEV_LOG 记录变更，PROGRESS 指向当前阶段，CHECK_LOG 记录专项检查。不能让四份旧文档各自成为新的执行清单。

**阶段关口**：

1. T01/T02 未过，不扩大真实数据相关测试或迁移。
2. T04 未证实官方 SDK 路径，记录技术阻碍并修正适配，不能用 mock 承诺 v1.0 Agent 完成。
3. T12 未过，不将报告保存数计为业务成功，不批量发布经验。
4. T13 未过，不声称已实现知识复利。
5. T16/T18 未过，不切换真实写入者。
6. T17 门槛未过，不发布正式 v1.0.0；内部演示如实标未完成。

**决定 BL1**：每次只做可验收小步骤；失败返还具体 T 任务，不另起一个失去历史的新“大重构”。

**决定 BL2**：一项风险只有实现证据通过才可关闭；“设计已吸收”与“运行已验证”分栏保存。

## 7. 最后的反向验收

发布前用以下问题反问一次，每一项都必须能指向实际证据：

1. 把模型关闭，资讯是否还能稳定抓取、保存、检索，并说明哪些判断不可用？
2. 把写入故意弄失败，是否真的没有成功状态和虚假知识链接？
3. 把资产版本拿走，是否诚实显示 unknown？
4. 让 pi 先输出好看的文字再报错，是否仍正确判失败/部分完成？
5. 工具执行后进程退出，恢复是否核对效果而非盲目重复？
6. 生成报告后没有实际排查结果，是否仍需要业务验收？
7. 下一次版本条件不同，是否指出经验失效部分？
8. 旧知识被反证推翻后，相关活跃事项是否可见复查提示？
9. 同时打开两页并断网重连，是否看到同一个最终状态？
10. 新系统产生数据后回退入口，新增成果是否仍在？
11. 用户只读重要变化、不建事项时，是否仍然获得有用的情报服务？
12. 不看任何实现名词，一个新用户能否完成问题到成果的工作？

设计审查结论：方案已覆盖目标闭环及主要反例，可以进入 T00 的实际开发准备。此结论不等于发布批准或功能验证通过；后续由任务书规定的证据决定是否推进。
