### 2.2 核心契约

```python
class ProviderHealth:                       # backend/services/ai_hub/provider_health.py — 唯一计数/判定源
    def record(self, provider: str, ok: bool) -> None    # 滑动窗口记账 (1min/5min/1h deque, 进程内不持久化)
    def is_unhealthy(self, provider: str) -> bool        # 窗口失败率超阈值 → 判定 (唯一真相源)
    def snapshot(self, provider: str) -> dict            # /api/llm/health 读这

class CircuitBreaker:                       # backend/utils/circuit_breaker.py — 薄状态机, 无独立计数
    state: Literal["closed", "open", "half_open"]
    opened_at: float
    def allow(self) -> bool                 # open 且未到 recovery_timeout → False; 到期 → half_open 放行 1 探针
    def trip(self) -> None                  # 由 health.is_unhealthy() 判定触发, 不自持 failure_count
    def reset(self) -> None                 # 探针成功 or 手动 (对齐 dsh runtime.reset_health 语义)
```

- **单一真相源 (审查 P0-1 修正)**: 旧稿"breaker 连续计数 + health 窗口"双记账会互相矛盾 (5 次散布 1h → 窗口判死而连续计数不触顶; 5 连败后恢复 → breaker OPEN 而窗口率已低)。定稿: **ProviderHealth 持有全部计数与判定, CircuitBreaker 只做状态机 (OPEN 期拒绝 / HALF_OPEN 探针 / 复位), trip 条件 = `health.is_unhealthy()`** — 不存在第二套失败计数
- **接入面完整 (审查 P0-2 修正)**: 图片生成路径 `image_service.py:84/:162` 是 httpx 直连, **不经过 gateway** — 两处必须同步 `health.record()`, 否则 health 数据闭环破缺 (deep/light 判健康而 image 实际挂); `tasks.py` evaluate 的同步 httpx 同查
- **keying = provider 级** (5 个 breaker, 不做 provider×scenario 的 15 态): 场景级避让交给 scenario_router 权重表 (deep 可在 ollama 健康时仍降权)
- **线程安全**: TriggerWorker 每票据独立短线程 + event loop 混跑 → health/breaker 状态统一 `threading.Lock` 保护 (仓内线程亲和教训)
- **调用链**: `services → gateway._try_order → [per-provider: breaker.allow()? → call → health.record(ok) → trip?] → 全部 OPEN → runtime fallback_order 兜底 (llm.yaml) → 结构化错误`
- **与 trigger_gate 边界**: trigger_gate 是 **user/入口级**限流 (队列前), breaker 是 **provider/出站级**熔断 (调用前) — 正交不重叠
- **与 dsh runtime 边界**: dsh 的 3 连败缓存保持独立 (进程级子进程语义, 其 LLM 出站不经 ai_hub), 通用 breaker 只管 ai_hub HTTP 出站; 若抽公共模式需同步迁移 dsh 测试 (裁决点 D2, 默认不抽)
- **可观测**: 每次状态迁移写 audit_log (对齐 Batch 2 LLM provider 审计链); `/api/llm/health` 暴露 state/failure_rate/last_error
- **场景感知** (§2.1 第 2 支柱): deep/light/image 三档各自 fallback 顺序落 `quality/scenario_router.py` 场景权重表 (deep 优先 sensenova → anthropic → ollama), health 数据作为排序输入; "配额感知" (RPM/TPM) 留 v0.8.2
