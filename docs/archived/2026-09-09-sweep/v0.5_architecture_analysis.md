### 1.2 用户日常操作流（高频路径）

**路径 A — 信息摄入（最高频）**
```
打开 → /data（或 /editorial）→ 浏览 7d 列表 → 点深读 → 收藏 → /data/favorites
```
- 现状：**双 UI**（/editorial 编辑风 vs /data 老版）并存，靠 Header "⇄ 版式" 按钮切换
- 痛点：**两边数据**（favorites / useSSE 等 hook）共享，但**版式不同** → 用户需切换习惯

**路径 B — 知识提炼（中频）**
```
/data 浏览 → 收藏 → /knowledge/process → /knowledge/compile → 概念学习
```
- 现状：knowledge/ 完整子路由树（12 页面）已上线
- 痛点：**与 editorial 没集成**——editorial 的 6 view 内 action / KL 复利是**前端 mock state**，真实数据要去 /knowledge/compound

**路径 C — 行动触发（低频）**
```
浏览 → /action/todos 看到待办 → /action/outbox 整理 → /action/report 出周报
```
- 现状：/action/* 有 9 个子路由，每个独立页面
- 痛点：**editorial action view** 与 **/action/todos** 是 **两套 UI** 同样功能

**路径 D — AI 助理（v0.5 新增，估时最低频）**
```
打开 AI view → 输入"查 24h AI 安全热点" → dsh 推理 → mcp__hotspot__search_hotspots → 返回结果
```
- 现状：**完全不存在**（vendor/dsh/ 未嵌入，AIView.tsx 不存在）
- 痛点：v0.5 投入 3 天工时，单人工作站日常使用频率未知

### 4.2 第一性原理 5 问

**Q1: 单人工作站的真实痛点是"信息过载"还是"AI 对话缺失"？**

实测证据：14 个 collector 24/7 摄入 → hotspots 表 2952 行 → 收藏/标签/简报/复利完整闭环。**用户痛点是"消化"，不是"对话"**。M4 dsh 集成 3 天工时对单人工作站的价值**未被验证**。

**Q2: "editorial 统一前端"会增加还是降低用户效率？**

SPEC §T8 说"老版式 M5 才物理删除，期间保持可回跳"——这意味着 **2-3 个月双 UI 期**。用户切换税（路径 A 在两版间跳）**未被任何 cost-benefit 分析量化**。

**Q3: "llm-wiki-2.0 数据底座"是 P5 终态吗？**

P5 已基本达成（knowledge_watcher + write_item_to_md 已实现 md 真源）。SPEC 把"语义升级"（confidence / 衰减 / 6 边）包装成"底座升级"——**虚增了基础设施价值，淡化了数据模型价值**。

**Q4: "ai_hub 单契约"的真实成本？**

SPEC §T19 估时 1.5d "单 PR 合并 836 行"。实测 ai_scores 表被 **3 个 trigger 文件直写**——合并 ai_hub 不改变 trigger 写路径。**真实成本 = 3 个 trigger 改造 + 836 行合并**，估时应为 3-4d。

**Q5: "M4 dsh 集成"是 R1 高/高风险，单人工作站能否承受？**

SPEC §8 风险表标"高/高"。dsh 0.1.0-rc 承诺 breaking change。**单人 = 唯一维护者**，承受不起 1 周降级 + 复盘成本。建议**降级到 v0.6+**，v0.5 先做价值已确证部分。

### 5.2 三大未识别盲点

**盲点 1 — 触发器层写路径分散**
- SPEC §T19 "ai_hub 单契约"假设：合并 836 行 service 就完事
- 实测：3 个 trigger 文件直写 ai_scores 表——grep 即便通过 service 层，写路径不在 service 走

**盲点 2 — 双 UI 切换税**
- SPEC §T8 "老版式 M5 才物理删除"——意味着 **2-3 个月双 UI 期**
- 实测 50 路由中，**28 个老版式路由 vs editorial 6 view**
- 用户切换成本：路径 A 在 editorial /data 间切换**需要重新建立认知地图**
- **修复**：建议"默认进 editorial，老版式仅作为 deep link 入口"，而非平级切换

**盲点 3 — dsh 集成价值未量化**
- SPEC 估时 3d M4，但 R1 高/高风险
- 单人工作站是否需要 AI 助理对话？**未做 user story 验证**
- 替代方案：用 grep + TUI（已有 AttentionHeatmap / BriefingMode / ScanMode 等6 种认知模式），无需 dsh

## 七、最终判断

**SPEC 战略正确**：统一前端 + 数据语义升级 + 性能收敛 → 单人工作站长期价值。

**SPEC 执行层失真**：
- 战略被"editorial 空壳 + 14 缺失"夸大驱动，**真实工作量约 60-70% SPEC 估时**
- 触发器层写路径分散**未被识别**
- dsh 高风险与单人维护能力的矛盾**未被正视**
- 双 UI 切换税**未被量化**

**建议路径**：
1. **M1 性能三任务独立发版**（v0.4.4）——脱离 v0.5 价值兑现路径
2. **M2-T4 + T5 推进**（低风险高收益，db 瘦身 + 契约首刀）
3. **M3-T6 拆 EditorialView + T7 子组件接 API**（2 子组件实测，不是 14 项）
4. **M3.5 优先 T12 衰减 + T13 6 边**（数据语义价值确证）
5. **M4 dsh 降级到 v0.6**（R1 高/高，单人维护能力边界）
6. **M5 拆 T19a + T19b**（service 合并 + trigger 改造）

**如果坚持完整 SPEC 流水线**：预计实际工时 14-16 人日（vs SPEC 估 21.5 人日），节省来自"14 缺失"与"editorial 空壳"的夸大。
