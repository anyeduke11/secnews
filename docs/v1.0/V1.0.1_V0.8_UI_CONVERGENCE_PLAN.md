# Hotspot v1.0.1 融合方案：v0.8 体验基线，v1.0.0 功能补充

> **~~已被取代 (SUPERSEDED 2026-09-08)~~**：本方案方向（v0.8 体验基线 + v1.0 功能补充）由 **v0.8.5** 正式接续并细化到路由/接口级，唯一权威 spec = [`docs/v0.8.5/V0.8.5_PLAN.md`](../v0.8.5/V0.8.5_PLAN.md)。差异要点：v0.8.5 反向收敛——恢复 v0.8 Sentinel 三层路由 `/` `/judge` `/action` `/garden`（本方案隐含接受了 C09 对三层的删除）+ 物理删除 V1SentinelShell + v1 四入口降级为重定向；并新增实现/验证分离的独立验收门（FactCheck + G1-G4）。本文其余原则（规格优先级、页面契约、验收故事）凡不与 v0.8.5 冲突者继续有效。

- 日期：2026-09-08；状态：待实施设计基线。
- 版本口径：`v1.0.0` 已完成代码收口并有本地标签，但业务闭环仍待 B0-B7 整改；本方案的实施版本为 `v1.0.1`。
- 决策：**v0.8 Sentinel 是唯一 UI/UX 基线；v1.0.0 的领域对象、可靠执行和六项能力作为功能层补入。**

## 1. 为什么这样合并

v0.8 已有清晰、连续的安全工作流：资料层发现变化，判断层组织证据，行动层形成结果。它的 Sentinel 壳、三层导航、管道状态和紧凑信息密度适合持续使用的安全工作台。

v1.0.0 的价值不在新增一套应用外壳，而在补足可追溯的工作对象和闭环：Material、Signal、Subject、Case、Judgment、Action、Run、Artifact、Knowledge，以及六项受管能力。此前“四入口”方案使这些功能与 v0.8 三层工作流并行，产生双导航、重复壳和页面间状态漂移。

本方案只裁决产品呈现与实施顺序。它不回退 v1.0.0 的数据模型、API 契约、迁移工具、技能注册或 B0-B7 业务整改，也不把代码层验证误写成真实业务闭环。

## 2. 规格优先级

| 层次 | 权威来源 | 在本方案中的作用 |
|---|---|---|
| UI/UX | `frontend/src/components/sentinel/SentinelShell.tsx`、`sentinel.css`、v0.8 Sentinel 页面 | 三层导航、视觉 token、信息密度、状态条、响应式与交互节奏的唯一基线 |
| 功能 | `docs/HOTSPOT_WORKSTATION_PRD_V1.0.md`、`docs/v1.0/contracts.md` | 九个领域对象、六项能力、审批、版本、产物、知识复用的功能边界 |
| 可靠性 | `docs/v1.0/REVIEW_2026-09-07.md` §6 | B0-B7 的依赖顺序和真实验收门槛 |
| 本方案 | 本文 | 将功能放入 v0.8 三层体验，处理路由、页面和迁移冲突 |

`docs/v1.0/V1.0.0_UI_UX_SPEC.md` 与 `design/UI_UX_CONTRACT.md` 中“四入口、V1SentinelShell、移除管道状态条”等规定，自本方案起不再作为新页面的导航与壳层依据；其中关于可访问性、错误状态、Case 详情、证据审阅、审批和移动端的条款继续有效。

## 3. 目标信息架构

主导航固定为 v0.8 的三层，不增加“今日工作”“情报”“事项”“知识”四个平行一级入口。

| 主层 | 主路径 | 用户的问题 | v1.0.0 功能补充 |
|---|---|---|---|
| 资料层 | `/` | 有什么新的、可信的变化影响我？ | Signal/Material 列表、事件聚合、Subject 关联、精选/待核实/历史视图、从证据创建 Case |
| 判断层 | `/judge` | 这些证据能形成什么结论，还缺什么？ | Case 队列与详情、Judgment、引用/反证/未知、对象快照、生成与人工修订 |
| 行动层 | `/action` | 已接受的结论要如何执行、验收和沉淀？ | Action、审批、Run、Artifact、验收、复盘、Knowledge 草稿与复查任务 |

知识不是第四个主层。它是行动的沉淀，也是可从“更多”进入的独立目录；在新的 Case 中，它通过判断和行动的“复用经验”入口出现。Case 也不是一级导航，它是判断层的工作容器，使用稳定深链接打开。

### 3.1 路由与兼容规则

| 路径 | v1.0.1 责任 | 兼容策略 |
|---|---|---|
| `/` | 资料层首页，保留 Sentinel 首页的主壳和管道状态 | v1 Signal/Material 查询替换或扩展现有资料列表，不新增第二个首页 |
| `/judge` | 判断层的 Case 队列；筛选、保存视图与待复查状态写入 URL | 可从列表进入 `/cases/:caseId/:section?` |
| `/action` | 行动层的待批准、运行中、待验收和复盘队列 | 项目按 Case、Run 或 Artifact 深链接进入相同 Sentinel 壳 |
| `/cases`、`/cases/:caseId/:section?` | Case 的兼容列表和详情 URL | 保留 URL；列表表现与 `/judge` 一致，详情不再渲染平行壳 |
| `/intel`、`/workbench` | 历史 v1 入口 | 保留深链接和 query，映射到资料层或相应队列，直到 B6 全量迁移验证通过 |
| `/knowledge` | 知识目录与复查 | 放在“更多”；保留旧静态子路径，不能由动态 ID 吞掉 |
| `/skill-store`、`/secnews`、`/garden`、`/settings` | 能力、兼容工作台、扩展与配置 | 均从“更多”或上下文入口到达，保留原有功能和数据 |

一个路由只能渲染一个应用壳。`SentinelShell` 是三层页面的最终壳；当前为 v1 四入口引入的 `V1SentinelShell` 仅可作为过渡适配器，收口时删除，不得继续扩展。路由和 URL query 是筛选、对象和返回位置的真相源，组件内 tab state 不能成为第二套导航。

## 4. 页面与交互契约

### 4.1 全局壳

- 保留 Sentinel 品牌、三层流程导航、主题切换、时钟和“更多”菜单。
- 保留全站管道状态条：源在线、收录、漏斗和队列。它反映的是 v0.8 采集运行面，不能被 v1 页面静默移除；后端不可达时显示 unavailable，而不是伪造零值。
- 继续使用现有浅/深主题和语义 token。工作区采用表格、列表、详情和抽屉，避免营销式 Hero、装饰卡片和嵌套卡片。
- 状态始终以文字和图标辅助颜色表达；loading、empty、unavailable、stale、partial、blocked、conflict、failed 与 accepted 的语义沿用 v1.0.0 规范。

### 4.2 资料层：从变化到 Case

资料层延续 v0.8 的情报阅读节奏：首屏是高价值变化、来源状态和可扫描的资料流，而不是统计卡片或聊天框。

每个事件显示标题、来源、时间、证据状态、关联对象和变化原因。用户可收藏、暂缓、查看原文、加入已有 Case 或创建 Case。创建只携带选中的 evidence IDs；推断和结论必须在判断层产生。待核实、历史资料和精选是明确视图，不用一个混合列表掩盖生命周期。

### 4.3 判断层：以 Case 承载研判

`/judge` 用 v0.8 判读台的双栏阅读结构：左侧是队列或证据，右侧是当前 Case 的研判上下文。Case 顶部固定显示问题、范围、对象快照、优先级、期限和阻塞原因。

证据与 Judgment 采用并列审阅。每个 claim 必须展示支持、反证、未知和引用定位；用户可补证、生成草稿、人工修订、接受、标记争议或发起行动。聊天只能作为带 Case 和证据版本的补充说明，输出仍需落入 Judgment 或 Action。

### 4.4 行动层：从批准到回执

`/action` 保留 v0.8 行动队列的操作密度，分为待批准、排队/运行中、待验收、需复查和已完成。Action 卡片显示目的、scope、计划版本、工具/权限、预算、预期成果和完成条件。

开始后，Run 时间线展示实际模式、步骤、日志、取消和恢复状态；不能以 mock 成功代替回执。Artifact 必须可预览或下载，并显示 hash、校验、预期与实际。只有“运行结束、校验通过、业务验收通过”三个状态均可解释时，才允许关闭 Case 或生成 Knowledge 草稿。

### 4.5 知识与能力

Knowledge 目录呈现已发布、待复查、弃用和撤回的经验，并保留适用条件、例外、证据链、版本和采用记录。行动层复盘产生草稿，判断层在新 Case 中发起条件比较和采用；来源关联不能计作采用。

六项能力不以编号或空白对话框暴露。它们分别从今日优先情报、Case 判断、已接受判断的行动、已验收成果复盘、新 Case 的经验采用和待复查队列进入。`/skill-store` 仍提供版本、依赖、自动触发和运行历史管理。

## 5. 功能映射与边界

| v1.0.0 能力 | 在 v0.8 体验中的位置 | 关键限制 |
|---|---|---|
| SourcePipeline、准入、Signal | 资料层与管道状态条 | fetched、accepted、persisted 分开显示；失败不得推进水位 |
| Subject | 资料/判断上下文抽屉 | 没有资产快照时标为待补充，不推断组织影响 |
| Case、Judgment | 判断层队列与详情 | 保持版本、引用和 `allowed_actions`，不以页面状态替代服务端守卫 |
| Action、Run、Artifact | 行动层队列与详情 | 审批绑定 `plan_hash`；取消和验收以真实运行回执为准 |
| Knowledge、adoption receipt | 行动复盘、判断复用与知识目录 | 条件比较和采用理由必填；失效知识不能作为高置信依据 |
| SK-01 至 SK-06 | 各业务对象的自然动作 | UI 只能展示后端报告为可用的能力；启用、自动触发、取消运行分开 |
| 20 个 legacy Skill | “更多”中的能力中心 | 保持兼容和可追溯，不能因导航收敛而静默删除 |

## 6. 实施批次

功能先获得真实输入和输出，再进入主界面。以下批次复用审查已定义的 B0-B7，避免为了视觉统一跳过可靠性整改。

| 批次 | 工作 | 退出条件 |
|---|---|---|
| U0：基线与壳收口 | 盘点 v0.8 Sentinel 页面、`V1SentinelShell`、`V1Prototype`、四入口路由和 CSS token；建立三层路由适配表 | 没有双壳、双主导航或内层主 tab；旧 URL 都有可验证目标 |
| U1：可信资料层 | 随 B0/B1 完成恢复保护、真实 SourcePipeline、准入和水位语义；将 v1 Signal/Material 接入资料层 | 单个真实来源可从抓取到列表追溯；失败、陈旧和部分成功可辨别 |
| U2：判断与真实执行 | 随 B2/B3 接入真实 dispatcher、dsh/pi、产物持久化、CAS 与 Case 关闭规则；在 `/judge`、`/action` 放入 mutation | 一条 Case 能在浏览器中补证、形成判断、批准、运行、验收，且关键失败不显示成功 |
| U3：知识与能力 | 随 B4/B5 完成 SSE 刷新、聚合查询、知识采用和六项能力 runner；收拢能力中心 | 第二个 Case 的真实采用产生一条 receipt；六项能力有输入、输出和失败态 |
| U4：迁移与发布 | 随 B6/B7 完成旧路由/数据对账、响应式截图、可访问性、性能和端到端验收 | 旧链接可回到同一工作上下文；G1-G5 与 PRD 验收矩阵有真实证据 |

每批先写反例测试，再实现服务或页面；前端每次路由和壳层改动至少执行类型检查、相关 Vitest、Vite build，以及 390/768/1024/1280/1440 的浏览器截图检查。涉及注册代码时仍运行 `python scripts/generate_meta.py --check`。

## 7. 验收故事

1. 用户在资料层看到一个新变化，打开真实原文并选择两条证据创建 Case。
2. 用户在判断层补齐对象版本，形成带支持、反证和未知项的 Judgment；没有证据时页面指出缺口。
3. 用户从行动层批准固定 `plan_hash` 的 Action，查看真实 Run 回执和可读 Artifact；取消、超时、重启和依赖缺失都显示实际结果。
4. 用户在同一处验收成果，关闭 Case 并生成带条件的知识草稿。
5. 新 Case 复用该经验时看到适用条件差异，选择采用并留下理由；采用记录增加一次，来源关联不增加采用数。
6. 用户刷新、后退或从旧 `/cases`、`/intel`、`/workbench` 链接进入时，仍回到相同对象和筛选；任一 API 失败不显示“暂无数据”。

## 8. 明确不做的事

- 不删除 v0.8 的三层导航、管道状态或既有 Sentinel 视觉语言。
- 不再扩充 V1Prototype 或 V1SentinelShell 为长期页面架构。
- 不因界面整合删除 `/secnews`、`/skill-store`、CodeGarden、CRM、收藏、搜索、阅读、TODO 或旧 Skill；B6 对账后才可逐项裁决。
- 不将 mock、静态种子、单元测试或页面渲染当作真实 dsh/pi、采集、执行和验收的证据。
- 不在 B0-B3 完成前扩大与业务闭环无关的新能力。

## 9. 成功标准

v1.0.1 完成时，用户面对的是一个 v0.8 风格的 Sentinel 工作台：一套三层导航、一套状态条和一套 URL 真相源。其背后具备 v1.0.0 的可追溯对象与闭环能力，能够从真实资料、证据判断、受控行动、成果验收到知识复用走完两次任务。

在 B0-B7 的真实验收未完成前，本方案仅代表已裁决的方向，不代表 v1.0.1 已发布或业务闭环已通过。
