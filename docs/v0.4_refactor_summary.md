## 1. 项目概况

**hotspot** 是面向 AI + 安全从业者的单人本地工作站，五个子系统共享一个 FastAPI 进程 + SQLite：

| 子系统 | 说明 |
|---|---|
| SecNews 热点聚合 | 采集 → 13 质量门禁 → 入库 → 趋势/搜索/导出 |
| Knowledge LLM-Wiki | 文件真相源知识库 + 6 认知模式 + 注意力评分 + FTS5 |
| CodeGarden | 项目生命周期 + 服务网格 + 资源中枢 + 联动引擎 |
| Security Graph | MITRE ATT&CK + CVE + 合规矩阵 |
| MCP Server | 工具暴露给外部 AI Agent |

**重构动机**：代码规模庞大（55 API / 81 service / 48+ 调度 job / 61 迁移 / 200+ 前端组件），但用第一性原理审视**实际数据流动**后发现：**"造了很多管子，但水只流了前四分之一"** —— 知识闭环在第 4 环后断流、KL 状态机被真相源抹除、5 张核心表 0 行、同步停机 26 天、服务网格 1,347 条噪音。

## 2. 审计方法论

### 2.1 第一性原理：价值链拆解

把每个子系统拆成**最小必要环节**，逐环节标注 已实现 / 部分 / 缺失：

```
Knowledge 价值链: 信息进入 → 分类 → 提炼concept → 关联 → 内化(复习/注意力) → 输出 → 复利反馈
                    ✅        ⚠️         ⚠️          ⚠️        ❌死代码        ⚠️        ❌空转
```

核心洞察：**完备性 = 代码存在 ≠ 数据流动**。判定标准不是"有没有这个函数"，而是"**这条链上有没有数据真正流过**"。

### 2.2 批判性审计：证据驱动

- **线上库直查取证**：所有结论附 `SELECT` 实测（如 `sm2_reviews=0`、`kl:publish=0`、`attention_events=0`、`cg_services 1347 条噪音`）
- **行号级证据**：每条发现带 `文件:行号`
- **四路并行子代理**：后端管道 / 知识同步 / CodeGarden 运维 / 前端 四组独立审计，产出 70+ 条发现，交叉印证

### 2.3 输出物

`docs/audit_first_principles_plan.md`（387 行）：Top15 问题排名 + 六组缺失清单 + 20 条业务流不清晰点 + **Phase 0-6 分阶段改进计划（含可量化验收标准）**。

## 5. 代码开发思路

### 5.1 三层修复原则：止血 → 数据流 → 体验
1. **先让系统不崩**（同步停机、job 崩溃、404）
2. **再让数据流动**（KL 状态、指纹、实体、注意力）
3. **最后统一体验**（导航、错误、主题）

### 5.2 数据真相源纪律
- **md 文件是真相源，SQLite 是读缓存** — 所有状态变更先写 md 再写 DB
- 状态机推进必须能在 full_sync 后存活（P1-1 的核心）
- 桥接表（item_entities）要有**明确的写入方**，否则就是死表

### 5.3 数据库迁移纪律
- 迁移**幂等**（`ALTER TABLE ... ADD COLUMN` 由 apply_migrations 容错）
- 全代码层修复优先于破坏性迁移（v0.4 全程 0 破坏性迁移）
- 对 live DB 的操作**先 dry-run 统计**再执行（如服务网格清理：先算会删多少行）

### 5.4 测试守护
- 每 Phase 结束跑全量回归（2,400+ 测试约 10 分钟，后台并行）
- **测试必须与真实行为对齐**：改行为就同步改测试断言（sm2 语义、多 collector 结构、KL 值）
- conftest 知识目录隔离（防止测试污染真实知识库）

### 5.5 可观测性
- 每个修复带可量化验收标准（"cg_services < 100"、"kl:publish > 0"）
- 失败可见（upsert 失败不再记 SUCCESS、源健康状态机真实推进）

## 6. 可固化经验（Harness 方法论）

以下是从本次重构提炼的、**可复用于任何 AI 驱动的大库重构**的方法论：

### 6.1 审计阶段
| 经验 | 说明 |
|---|---|
| **价值链拆解** | 任何系统先画"最小必要环节链"，逐环节问：数据流到这里了吗？ |
| **代码存在 ≠ 功能可用** | 判定标准是**表里有没有数据**、**有没有调用方**，不是有没有函数 |
| **线上库直查取证** | `SELECT COUNT(*)` 是审计的最强证据，比读代码更真实 |
| **死代码四连查** | grep 无引用 / 表 0 行 / 无调用方 / 只被测试引用 |
| **并行子代理分工** | 按子系统边界分 4 组审计，各自带行号证据回传，交叉印证 |

### 6.2 重构阶段
| 经验 | 说明 |
|---|---|
| **止血先行** | 先修"系统级错误"（崩溃/停机/404），再修"数据断裂"，最后修"体验" |
| **小步提交** | 每个 Phase 一个提交，消息含"问题→修复→验收"三段式 |
| **行为变更必改测试** | 改了语义（sm2 晚者胜、多 collector）就必须同步改断言，否则测试是负担 |
| **live 操作先 dry-run** | 清理/回填/迁移前先算影响行数 |
| **失败即中止 vs 静默空表** | 同步类操作：区分"表缺失=合法空"与"真失败=必须中止"（防误删） |

### 6.3 技术模式
| 模式 | 应用 |
|---|---|
| **入库后补写** | 依赖 FK 的写入（指纹）移到主行入库之后 |
| **桥接表 + 明确写入方** | item_entities 从 0 行到 34 行，关键是给了它写入方 |
| **fail-closed 门禁** | 门禁崩溃转 passed=True 会让"最后防线"失效 → 改为失败+扣分 |
| **动态引用模块属性** | `from module import X` 在 import 时绑定；测试 monkeypatch 需动态 `module.X` |
| **双 FTS 表路由** | unicode61（ASCII）+ trigram（CJK≥3字）+ LIKE（短查询） |
| **多 collector 结构** | `dict[Category, list[Collector]]` 支持一分类多采集器 |

### 6.4 验收标准（每个修复必须有）
```
可量化: "cg_services 1,347 → <100" / "kl:publish > 0" / "item_entities > 0"
可验证: 全量测试回归 + 线上数据直查
```

## 7. 踩坑与教训

| 教训 | 详情 |
|---|---|
| **`__all__` 块编辑事故** | 用 sed/python 字符串替换插入新 job 时，误把新代码插进 `__all__.extend([...])` 列表中间 → 语法错误；修复时块删除连带删掉了 10+ 个 job 函数定义。**教训：大文件编辑用精确锚点，改完跑语法检查 + 函数计数** |
| **CHECK 约束静默吞数据** | `INSERT OR IGNORE` 遇 CHECK 失败**不报错不插入**，item_entities 写了 `source='enricher'` 非法值 → 0 行且无提示。**教训：OR IGNORE 会吞掉所有约束错误，先查表 DDL 的 CHECK** |
| **import 时绑定 vs monkeypatch** | `from knowledge_sync import ITEMS_DIR` 在 import 时绑定旧值，测试 conftest 重定向后服务读不到。**教训：可被 patch 的模块属性用动态引用** |
| **测试写真实库** | 旧 chunks 测试写真实 `knowledge/items/`（依赖 API 的 `__file__` 路径），重构后暴露。**教训：测试文件一律写重定向目录** |
| **状态机要覆盖初始态** | SourceHealthMachine 只处理 active/stale/dead/grace，seed 的 `unknown` 永远不被处理 → 130 源永远 unknown。**教训：枚举状态机必须覆盖所有可能初值** |
| **并发共享可变状态** | collector 的 `self.sources` 在并发 collect 间互相覆盖 → 统一 asyncio.Lock |
| **语义反转的 merge** | sm2 "due_at 早者胜" 实为反的（复习后 due_at 变晚）→ 改晚者胜 |
